# Writing Guidelines

Comprehensive guidelines for language, tone, clarity, and formatting in meeting review reports.

## Language and Tone

### Professional Business Communication
- **Maintain business-appropriate tone** throughout the document
- **Technical yet accessible**: Use proper terminology but explain complex concepts
- **Clear and direct**: Avoid ambiguity and unnecessary wordiness
- **End-user perspective**: Write as if explaining to stakeholders who weren't in the meeting

### Voice and Structure
- **Active voice preferred**: "The team decided" instead of "It was decided"
- **Subject-verb-object clarity**: Make it clear who did what
- **Avoid passive constructions** unless necessary for emphasis or diplomacy
- **Strong verbs**: Use action verbs that convey specific meaning

Examples:
- ✓ "The engineering team implemented the new API structure"
- ✗ "The new API structure was implemented"
- ✓ "Management approved the budget increase"
- ✗ "The budget increase was approved"

### Terminology Consistency
- **Use same terms** for same concepts throughout the report
- **Define acronyms** on first use: "API (Application Programming Interface)"
- **Maintain technical accuracy**: Verify technical terminology
- **Create glossary** mentally as you write to ensure consistency

Examples:
- If you start with "database migration," don't switch to "DB transfer" later
- If you use "sprint planning," maintain this term rather than alternating with "iteration planning"

## Clarity and Precision

### Avoiding Ambiguities
- **Be specific** rather than vague
- **Quantify when possible**: Include numbers, dates, metrics from meeting transcript
- **Name names**: Use actual participant names, not "someone" or "a team member"
- **State what is known** and acknowledge what remains uncertain

Examples:
- ✓ "The team will deliver Phase 1 by March 15, 2024"
- ✗ "The team will deliver soon"
- ✓ "John Smith raised concerns about the API response time"
- ✗ "Someone mentioned API issues"
- ✓ "The deadline was discussed but not finalized (see open points)"
- ✗ "A deadline was mentioned"

### Separating Complex Concepts
- **Break down complicated ideas** into discrete, manageable components
- **Use clear paragraph breaks** to separate distinct concepts
- **One main idea per paragraph** as a general rule
- **Transitional phrases** to show relationships between ideas

### Handling Uncertainty
- **If transcript is unclear**: State what is known and what remains uncertain
- **Use appropriate qualifiers**: "appears to," "suggested," "indicated"
- **Flag ambiguities**: "Two interpretations are possible..."
- **Never fabricate** details not present in the transcript

Examples:
- ✓ "The discussion suggested three possible approaches, though a final decision was not reached"
- ✗ "The team decided to use the third approach"
- ✓ "John mentioned a deadline, but the specific date was not captured in the meeting"
- ✗ "John set the deadline for June 15"

## Formatting Strategy

### Bold Text Usage
**Use bold text for:**
- All decisions
- All open points
- All action items
- All critical aspects (risks, priorities, constraints)
- All assignee names
- Deadlines when especially important

**Example formatting:**
- "**Decision**: The team will migrate to PostgreSQL 15"
- "**Open Point**: Database backup strategy requires further discussion"
- "**Action**: **John Smith** will conduct performance testing by March 15"
- "**Risk**: Migration downtime may exceed the planned 4-hour window"

### Bullet Points
**Use bullet points for:**
- Lists of related items
- Discussion points within a theme
- Risks or constraints
- Requirements or specifications
- Related themes in dependencies

**Best practices:**
- Keep bullets parallel in structure
- Start each bullet with strong verb or noun
- Maintain consistent grammatical form
- Use sub-bullets for hierarchical information

### Numbered Lists
**Use numbered lists for:**
- Sequential steps or processes
- Prioritized items (1 = highest priority)
- Ordered actions that must occur in sequence
- Multiple related actions by same assignee

**Best practices:**
- Use when order matters
- Maintain logical sequence
- Make steps clearly actionable
- Include enough detail at each step

### Headers and Subheaders
- **Section headers** (##): Introduction, Discussed Themes, Summary, Follow-up
- **Subsection headers** (###): Individual theme titles, summary subsections
- **Sub-subsection headers** (####): Use sparingly, only when hierarchical structure needed
- Keep headers **descriptive and specific**: "Database Migration Strategy" not "Database"

### Paragraph Structure
- **Topic sentence**: Lead with main idea
- **Supporting details**: Provide context and specifics
- **Conclusion or transition**: Connect to next idea
- **Length**: 3-6 sentences typically; break up longer paragraphs
- **Avoid walls of text**: Use paragraph breaks liberally

### Tables (Optional)
Consider tables for:
- Multiple action items with consistent attributes
- Comparison of options discussed
- Timeline or schedule information
- Resource allocation data

**When to use tables:**
- 5+ items with 3+ consistent attributes
- Information needs side-by-side comparison
- Scanning efficiency is critical

## Emphasis and Highlighting

### Creating Scannable Documents

**Executives need to find information quickly. Apply these techniques:**

1. **Strategic bolding**: Bold key terms that busy readers need to find
2. **Whitespace**: Generous use of paragraph breaks
3. **Bulleted summaries**: Pull out key points
4. **Headers as signposts**: Make section purposes obvious
5. **Lead with conclusions**: State decisions/outcomes upfront

### Decision Emphasis
**Every decision should be:**
- Preceded by "**Decision**:" label (or similar)
- Bold text for the decision statement
- Followed by brief context or rationale
- Easy to locate by scanning

### Action Item Emphasis
**Every action should have:**
- Bold assignee name
- Clear action verb
- Specific deliverable
- Timeline when available
- Easy visual separation from surrounding text

### Critical Aspects Emphasis
**Risks, priorities, and constraints need:**
- Bold labels: "**Risk**:", "**Priority**:", "**Constraint**:"
- Prominent placement in relevant theme sections
- Consolidation in Summary section
- Clear articulation of impact

## Cross-Referencing

### Internal References
- Reference other themes by name: "See Database Migration Strategy theme"
- Link related sections: "As discussed in the Summary section..."
- Connect dependencies: "This action depends on completion of Theme X"
- Build narrative flow across sections

### Creating Coherent Narrative
- **Introduction previews** themes covered
- **Themes reference** related themes when discussing dependencies
- **Summary consolidates** information from themes
- **Follow-up connects** actions back to themes

### Dependency Mapping Language
- "This theme depends on [Theme Name]"
- "Prerequisite: [Theme Name] must be completed first"
- "Related to [Theme Name], which addresses [aspect]"
- "Blocks: [Theme Name] until this is resolved"

## Language-Specific Guidelines

### Italian (Default)
- Use formal business Italian throughout (formal register)
- Technical terms: Use English technical terms when industry-standard (e.g., "API," "cloud," "database")
- Date format: DD/MM/YYYY or "15 marzo 2024"
- Decision labels: "**Decisione**:", "**Punto aperto**:", "**Azione**:"
- Professional tone: Formal but not overly bureaucratic

### English
- Use international business English
- Avoid regional idioms or colloquialisms
- Date format: March 15, 2024 or 2024-03-15
- Decision labels: "**Decision**:", "**Open Point**:", "**Action**:"
- Professional tone: Clear, direct, respectful

### Other Languages
- Maintain professional business tone appropriate to the culture
- Use industry-standard technical terms (often English)
- Apply appropriate formality levels
- Use culturally appropriate date/time formats
- Verify decision/action labels are grammatically correct

## Stylistic Preferences

### Sentence Structure
- **Vary sentence length** for readability
- **Start with strong subjects**: People, teams, specific entities
- **Use concrete nouns**: "The engineering team" not "resources"
- **Minimize modifiers**: Strong verbs reduce need for adverbs

### Paragraph Flow
- **Logical progression**: Ideas build on each other
- **Transitional phrases**: "Additionally," "However," "As a result," "Furthermore"
- **Coherent themes**: Each paragraph develops a single main idea
- **Connect to context**: Relate back to meeting objectives

### Professional Tone Maintenance
- **Objective reporting**: Present facts and decisions without personal commentary
- **Diplomatic language**: When reporting disagreements or concerns
- **Constructive framing**: Focus on solutions and next steps
- **Respectful references**: Use proper titles and names

## Common Pitfalls to Avoid

### Language Pitfalls
- ✗ Excessive jargon without explanation
- ✗ Inconsistent terminology
- ✗ Passive voice overuse
- ✗ Vague or ambiguous statements
- ✗ Overly complex sentence structure

### Formatting Pitfalls
- ✗ Walls of text without breaks
- ✗ Inconsistent bolding or emphasis
- ✗ Missing headers for themes
- ✗ Bullets and numbered lists mixed incorrectly
- ✗ Poor visual hierarchy

### Content Pitfalls
- ✗ Fabricated details not in transcript
- ✗ Assumptions presented as facts
- ✗ Missing key decisions or actions
- ✗ Incomplete action items (no assignee)
- ✗ Unacknowledged uncertainties

### Structural Pitfalls
- ✗ Sections out of order
- ✗ Inconsistent theme structure
- ✗ Summary introducing new information
- ✗ Follow-up lacking clear accountability
- ✗ Missing cross-references for dependencies
