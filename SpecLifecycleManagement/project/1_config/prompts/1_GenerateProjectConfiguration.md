# Prompt — Generate a Claude Project for Documentation & Spec Lifecycle Management in Spec-Driven Development

---

## Role

Act as a full-stack software engineer with 20+ years of experience, specialized in spec-driven development and in the practical use of generative AI coding agents (Claude Code and equivalents) on large, long-lived production codebases. You have direct experience with the failure modes of AI-assisted documentation at scale. You are opinionated, concise, and you flag disagreement rather than accommodating a premise you think is wrong.

## Task

Produce **three downloadable artifacts** that together configure a Claude Project dedicated to the theme described below. Do not produce a single combined document, and do not deliver the content inline in chat only — each of the three must be a separate downloadable file:

1. **`project-description.txt`** — a synthetic project description in plain text (`.txt`), suitable for pasting into the "What are you trying to achieve?" / project description field when setting up a Claude Project.
2. **`project-overview.md`** — a detailed and exhaustive description of the project in Markdown (`.md`), intended to be uploaded as the primary knowledge document of the project.
3. **`project-instructions.md`** — the project instructions in Markdown (`.md`), intended to be pasted into the Claude Project's custom instructions field, so that every conversation started inside the project inherits the right context, constraints, and behavior.

All three deliverables must be written in **English**.

## Domain Context — read fully before producing anything

### The workflow in use

Every development session follows this sequence:

1. **Brainstorming** — sharing and exploring ideas.
2. **Specification** — writing a design spec / feature spec.
3. **Implementation plan** — the spec is transformed into a detailed development plan.
4. **Implementation** — execution driven by the plan, frequently parallelized across sub-agents.
5. **Code review**, followed by bug fixing and subsequent modifications as needed.

This structure is deliberate and must be preserved. Any recommendation that requires abandoning or restructuring it is out of scope. Interventions graft onto the existing phases; they do not add phases.

### Environment

- Claude Code as the primary coding agent, with a plugin-based workflow (`brainstorm → design spec → implementation plan → sub-agent execution`).
- A codebase knowledge graph built via Tree-sitter plus LLM semantic extraction, used for navigation and orientation, and queryable from the CLI.
- Large, long-lived enterprise codebase; any arbitrary technological stack.
- Significant amounts of accumulated project documentation, in-code comments, specs, implementation plans, and years of revisions and bug-fix history.
- All documentation and specification maintenance work is performed **by coding agents**, not by hand. This is a hard constraint: every recommendation must be executable by an agent and verifiable by a human reading a diff. The one exception is recorded explicitly under *Recommended sequencing*, and it is exceptional precisely because the open question behind it is unresolved.

**Stack neutrality.** Nothing produced may depend on a specific technological stack. Where this prompt names concrete technologies (.NET, React, TypeScript, SQL, SAP B1, SAP B1 Service Layer, Beckhoff TwinCAT), they are **illustrations of a category** — "an external constraint the code cannot state about itself" — and must be presented as such in the deliverables, never as project facts or as a committed stack.

**Stack neutrality applies to mechanisms, not only to code.** Some interventions below (notably retrieval exclusion, review-unit identification, and post-merge sha resolvability) are specified as required **capabilities** with named channels but no named tool, because every concrete implementation of them — ignore files, index configuration, glob patterns, graph exclusion lists, PR-level checks, merge strategies — is toolchain-specific. Where a cost claim or a control depends on such a mechanism existing, the deliverables must state that the claim is conditional on the toolchain providing it, rather than asserting the cost or the control as known.

### The observed problem

On a large codebase with heavy documentation history, AI agents asked to change a business rule, a spec, or a comment consistently **append a revision** instead of **editing the existing content**. They add "Revision 3", "Update 2026-07-14", stacked layers of historical notes, and references to old bug fixes.

This has real upside: history is preserved, past problems remain traceable, and context is richer. But it also:

- inflates token consumption and fills the context window;
- injects obsolete and outdated information into the working context;
- produces documents in which multiple statements contradict each other, with no ordering signal telling the agent which one is current;
- makes the eventual consolidation pass increasingly expensive and increasingly risky.

The need is therefore **periodic consolidation**: collapsing accumulated revisions into a single, complete, current, non-contradictory statement of the truth — across project documentation, specs, implementation plans, and in-code comments — without silently losing information that still matters.

### Diagnosis to encode in the project

The append behavior is not a defect; it is a rational response to an incentive. Deleting information requires knowledge the agent does not have (*is this still true? does anything depend on it?*), while appending is always safe — it never loses anything, and the cost it imposes is paid later, by someone else, in a different session. Unless a document explicitly states where history lives, the agent assumes history lives in that document and preserves it.

A practical consequence: instructing agents to "be concise" or "avoid redundancy" does not fix this, because it does not change the incentive. Changing the incentive means telling the agent, in the artifact itself, where history belongs instead.

The root cause is that documents are performing two incompatible functions simultaneously: **describing current state** and **recording history**. These have opposite lifecycles — the first must be rewritten, the second is immutable by definition. Keeping both in the same file guarantees accumulation.

### Units of account — fix these three terms before anything else

Several bounds and checks below are scoped to one of three units, and the design is unreadable if they are conflated. Define all three in the deliverables.

**The review unit.** Everything a single human review pass is expected to read — the pull request in the merge-time case, and the standalone commit or commit set constituting one consolidation pass in the brainstorming-time case. Commits subdivide a review unit for readability; they do not create additional review capacity. Because bounds are enforced against it, a review unit must carry an identity a script can read: the enforcement mechanism cannot accumulate across a unit it cannot delimit. The identity is declared in the header of the classification record, alongside the unit rule and the declared scope; the concrete mechanism that surfaces it to the gate is toolchain-specific and left open below.

**The declared scope of a pass.** The set of classifiable units the pass commits to examining — normally a set of whole files, and, where a single file alone would exceed the bounds of a review unit, an explicitly enumerated subset of one file. It is stated in the header of the classification record alongside the declared unit rule, and it is what the coverage check counts against. Coverage is a claim about the declared scope, never about the file system.

**The classifiable unit.** The smallest thing a classification entry refers to. It has no global definition, because document structures differ and source files differ from prose; it is fixed **per pass** by the unit rule the pass declares in its record header (illustratively: a Markdown block-level element, a comment block, a single comment line, a numbered list item). The coverage check counts against the declared rule, which is what makes it implementable regardless of which rule is chosen. Which rule is *good* for documents without clean paragraph boundaries remains open below.

### Artifact taxonomy (the primary intervention)

| Artifact | Function | Lifecycle |
|---|---|---|
| Spec / design doc | **State** | Present tense, describes the system as it is now. No "Revision N" sections. When a business rule changes, the sentence changes. Re-aligned to reality at merge time, not only before implementation. |
| Implementation plan | **Ephemeral** | Has a death date. Marked `status: completed` mechanically at merge; archived later at the author's discretion; **excluded from all retrieval channels** once archived — indexes, globs, knowledge graph, **and inbound references from surviving documents**. |
| ADR | **Append-only log** | One file per decision, immutable, with `status: accepted \| superseded-by ADR-NNN`. All historical rationale that currently pollutes specs belongs here. |
| Code comments | **State** | Explain why the code is the way it is *now*. Never "fix for bug #1234" — that is a commit message, already in git. |

**Reconciliation of merge-time realignment with the separate-commit rule.** "Re-aligned to reality at merge time" and "consolidation is always a separate commit, never mixed with functional changes" are reconciled as follows: the realignment is **a separate commit inside the same pull request** as the functional change. Same PR, distinct commit, independently readable diff. State this resolution explicitly in the deliverables rather than leaving the reader to infer it.

**Consolidation without a host PR.** The merge-time case is not the only one. A consolidation triggered at the start of brainstorming (see *Triggers*) has no functional change to accompany and therefore no host pull request; it stands alone as its own commit and, where the workflow requires review, its own pull request. The invariant is *never mixed with functional changes*, not *always inside a feature PR*. Say this explicitly, because the same-PR reconciliation above otherwise reads as a requirement to find a host PR that does not exist.

### Positions already settled — treat these as decided, do not re-litigate

#### On comments and the regenerability test

- The source of truth about *what the system does* is **the code itself**, not the comments. Comments can lie, and are the only artifact in the repository that can lie without immediate consequence — no test breaks. Comments must therefore be **compacted, not annotated**: they should carry only current truth.
- The operational rule for comments is not "keep comments true" but **"reduce the surface of what can lie."** A comment that restates the code must be **deleted, not compacted** — it adds nothing and can diverge. This category is large in AI-assisted codebases, because models comment generously by default.
- The bright line for "restates the code" is **regenerability**: if the comment could be reconstructed from the signature, the identifiers, and the control flow alone, it is redundant and is deleted. If reconstructing it would require knowing something not present in the file, it is not redundant, however obvious it looks. This test exists because "looks redundant" is exactly where an LLM misjudges — a one-line comment stating an invariant reads like a restatement.
- **Every deletion made on regenerability grounds records its basis.** The classification entry for a deleted comment names what reconstructs it — which signature, which identifiers, which control-flow structure. This costs one clause per entry and converts the weakest link in the design from an unexaminable judgement into a spot-checkable claim: a reviewer can read the basis and the `-` line together and disagree. An entry whose basis amounts to restating the comment is not a basis and fails review.
- Only comments carrying what the code cannot say about itself survive: the reason for a non-obvious choice, an external constraint (illustratively: SAP B1 / Service Layer behavior, a TwinCAT quirk), a rejected alternative and why, an invariant not expressible in the type system. This category must be **defended conservatively** during consolidation. The failure modes are asymmetric: keeping one redundant line costs tokens, deleting one genuine invariant costs a defect.
- Historical bug-fix references in comments are not to be compacted but **relocated** — to a commit message or an ADR.
- **A comment that disagrees with the code is not automatically a stale comment.** The agent can observe divergence; it cannot determine which side is wrong, because it cannot distinguish intended behavior from a defect. Divergence is therefore **escalated as a suspected defect**, never silently resolved by rewriting the comment to match the code. Without this rule, the comment-consolidation skill launders bugs into documentation, and the laundering is invisible in review precisely because the resulting comment is accurate about the code.
- **In a code-comment pass, the `not verifiable` bucket has no in-file carrier, and none is to be invented.** A source file has no front matter and no place for a `## To be confirmed` section, and per-comment meta-annotation is prohibited outright. The resolution: a comment classified `not verifiable` is **left in place, byte-for-byte unmodified**, and the escalation travels entirely through the out-of-file channels — the classification record for the pass and the escalation intake below. This is a deliberate asymmetry with document passes, where the same bucket lands in a `## To be confirmed` section visible to the next reader of the file. Its consequence is that an unverifiable comment is invisible to anyone who opens the file, which weakens escalation for the very skill most likely to run first; that consequence is recorded as an open question rather than patched with an annotation.
- **Freezing under the `not verifiable` label happens at the declared unit, and a coarse unit rule therefore freezes redundancy along with the unverifiable content.** A comment block labelled `not verifiable` is preserved whole, including any regenerable lines inside it; the pass does not reach into a frozen unit to compact part of it. A pass that needs finer resolution declares a finer unit rule — a single comment line rather than a block — and accepts the higher entry count and the larger spot-check surface that follows. Do not present this as a defect to be engineered around: it resolves in the cheap direction of the standing asymmetry, since a frozen redundant line costs tokens while reaching into a frozen unit risks the deletion the label exists to prevent.

#### On the bounds that make diff-based review real

- **Because the regenerability test is the weakest link, the volume it is applied to must be bounded.** The test is fallible in exactly the direction that costs a defect, and the only control on it is a human reading `-` lines. A consolidation whose removed content exceeds what a reviewer will actually read has no control at all — the diff-based review guarantee is nominal.
- **The bound on a consolidation review unit has two parts, because two different things exhaust the reviewer.** Reading volume is exhausted by removed lines; judgement volume is exhausted by the number of independent deletion judgements the reviewer must be willing to accept. These do not move together: one forty-line removed block is one judgement, while forty removed one-line comments are forty, and a line-only cap treats them as equivalent. Every consolidation review unit therefore carries **both** a cap on removed lines **and** a cap on the number of entries carrying a regenerability basis. A pass may breach neither. Both numeric values are to be calibrated by observation and must not be invented in the deliverables.
- **Both parts of the bound are scoped to the review unit, not to the commit, and splitting does not raise them.** Review capacity is a property of the human reading the pass, so a bound enforced per commit is evadable by arithmetic: four commits of two hundred removed lines each satisfy a two-hundred-line per-commit cap and still present the reviewer with eight hundred lines. A pass that would exceed either part is therefore **split across review units** — separate PRs, or separate passes on separate days — not across more commits inside the same one. Subdividing into multiple commits within a review unit remains encouraged for diff readability and remains subject to the same totals.
- **The bound applies to every consolidation review unit, not only to comment passes.** Its justification is review capacity, and review capacity is a property of the human, not of the artifact type: a spec consolidation that removes eight hundred lines is exactly as unreviewable as a comment consolidation that removes eight hundred lines. Whether the *numeric values* should differ by artifact type — removed prose and removed comment lines are not equally dense, and prose deletions rarely carry a regenerability basis at all — is deliberately left open below. The bound is a review-capacity constraint, not a quality metric.
- **The bound and the spot-check draw on the same budget and are calibrated as one decision.** The bound exists because a human must read the `-` lines and accept the deletion judgements; the entry spot-check (see the consolidation procedure) exists because reading `-` lines does not detect skimming. All of it consumes the attention of the same reviewer in the same pass, so any of the three numbers chosen without the other two defends nothing: raising one silently degrades the others. The deliverables must present the review budget of a unit as one quantity with three claims on it — removed lines to be read, deletion judgements to be accepted, entries to be spot-checked — and must state that the three numbers are calibrated together or not at all.
- **Enforcement must run at a gate that can see the whole review unit.** A pre-commit hook cannot see a pull request, so in the merge-time case a pre-commit hook is insufficient by construction: it can only ever enforce a per-commit total, which is the evadable bound this design rejects. Enforcement therefore runs at whatever gate observes the complete unit — a PR-level check in the merge-time case, a pass-level check reading the review-unit identity from the classification record header in the standalone case. Specify the requirement; the concrete gate is toolchain-specific and left open below.
- **The three tiers are a partition of authority, not an independent control on the regenerability test.** Tier assignment is itself a judgement the agent makes before it knows the answer: it cannot know a comment states external truth until it has already decided the comment is not regenerable. A deleted regulatory constraint *is* a tier-3 item misclassified as tier-1, so the tier table cannot be presented as the safety net that catches regenerability errors — it is the same judgement wearing different labels. The only controls genuinely independent of that judgement are the two-part bound and the citation-plus-spot-check. State this in the deliverables wherever the tier table appears, or the table will be read as protection it does not provide.

#### On plans

- Implementation plans are **archived, not deleted** — but archived plans must be invisible to retrieval. A readable archived plan is worse than a deleted one: it carries the authority of a spec and the content of an intention.
- Plan status marking (`completed`) happens **at merge, immediately**; physical archiving happens **later, at the author's discretion**. These two events are deliberately decoupled. The reason: between merge and archiving, a live plan saying "I will do X" coexists with a spec saying "the system does Y", and if implementation diverged from the plan (it always does), the agent has two sources in conflict and no criterion for preferring one. The status field supplies the criterion at zero cost, independently of when the file physically moves.
- **The archiving script owns the archived-plan inventory.** Once a plan is excluded from the knowledge graph, the graph can no longer be queried to find plans that were archived but never status-marked, or status-marked but never archived. That reconciliation is therefore a responsibility of the archiving script, which maintains its own record of what it moved and when — it is not a knowledge-graph query and must not be specified as one.
- If, at the end of a feature, the plan contains information that would be painful to lose, that information belonged in the spec or in an ADR and never made it there. It is a signal about a missed transfer, not a reason to keep the plan alive. The correct response is to move the content to its proper artifact, then let the plan die on schedule.

#### On markers

- **Default is implicit:** unmarked content is current. Annotating a paragraph as "still true" is noise that ages worse than the content itself — a six-month-old `verified: true` is a false claim wearing a guarantee.
- **No meta-annotation inside code comments, ever.** A comment describing the verification status of another comment is the bottom of the barrel.
- The only persistent marker worth defending is per-document, not per-paragraph: `last-verified-at: <commit-sha>` in the front matter. It costs nothing, ages informatively rather than deceptively (a sha 400 commits behind is a real signal; a stale `verified: true` is a lie), and gives the agent a signal about how much to trust the file. It applies to documents with front matter; code comments have no such carrier, which is consistent with the prohibition above.
- **The sha recorded in `last-verified-at` is the commit the document was verified *against*** — the repository state the agent read while classifying, i.e. the `HEAD` in effect at the start of the classification pass — **not the consolidation commit that writes the field.** Recording the consolidation commit would be circular: its sha does not exist until after the file has been written. This resolution matters because the field's whole value is as a distance measure against the code, and the code state that was actually examined is the parent, not the child.
- **The recorded sha must remain resolvable in the integration branch after merge.** A sha the reader cannot resolve is not a weaker distance measure, it is the same class of lie as a stale `verified: true` — and in the merge-time case the baseline is a feature-branch commit, which a squash or rebase merge destroys. The field is therefore only admissible where the toolchain and merge strategy guarantee resolvability, or where a mechanical post-merge step maps the recorded sha to a surviving one. Which of those applies is toolchain-specific and left open below; what is settled is that a dangling sha is not an acceptable outcome and that the field is omitted rather than written unresolvable.
- **`last-verified-at` is written only by a pass whose declared scope is the whole document.** A subset pass — one that consolidated part of a file because the file alone would exceed the bounds — does not write the field, because writing it would assert verification of content the pass never examined. This follows directly from the requirement that a control measure the property it is credited with: a `last-verified-at` that means "most of this file was checked" is the same class of lie as a stale `verified: true`. The corollary is that a document consolidated across several review units carries no verification marker until the last of them completes, and that the tracking of the outstanding remainder is an open question below — deliberately not solved by inventing a partial-verification marker.
- **Isolation by commit is mandatory whenever the pass realigns a document to a functional change; stashing is admissible only for a standalone pass.** The two are not interchangeable, and the baseline resolution above is what decides it: if the functional work is stashed rather than committed, the captured `HEAD` predates the change the document is being realigned to, so the agent verifies the document against code that does not yet contain the behavior in question — the exact failure the fixed ordering exists to prevent. Commit the functional work first in the merge-time case. Reserve stashing for a brainstorming-time consolidation that happens to have unrelated work in flight, where the captured `HEAD` and the tree the agent reads coincide.

#### On retrieval exclusion and deletion

- **Retrieval exclusion is the primary lever; deletion is the secondary one.** The same mechanism that makes archived plans invisible to retrieval works on any low-value document, at far lower risk and with no unrecoverable step. Deletion's marginal gain over exclusion is small; its downside is unrecoverable. Deletion is therefore a **two-phase operation**: exclude from retrieval first, delete later if nothing missed it.
- **Exclusion is only as strong as its weakest channel.** An excluded file remains reachable by direct path from cross-references in surviving documents, and remains findable by a full-text search of the working tree. Phase one is therefore **exclude *and* sever inbound references** — otherwise part of the context cost stays in place and the claim that deletion "buys almost nothing extra" does not hold. Channels to be closed explicitly: retrieval index, glob patterns, knowledge graph, inbound links from documents that remain in play. Reachability by a deliberate full-text search of the tree is accepted as residual and is not a reason to prefer deletion.
- **Exclusion is recoverable, but not costlessly, and the deliverables must not overstate this.** Restoring an excluded file is a configuration change; restoring the inbound references that were severed is a revert against documents that have themselves been edited since, so the recovery cost rises with elapsed time and with the churn of the severed documents. State the property as *no unrecoverable step, with recovery cost rising after the fact* — not as *no irreversible step*. The comparison with deletion still favors exclusion decisively; the margin is just smaller than an unqualified claim suggests.
- **Severing inbound references is a destructive edit on documents that stay in play, and is governed as one.** It removes lines from surviving specs and docs, so it is a separate commit, it counts against the bounds of its review unit, and it is reviewed by reading the `-` lines like any other consolidation. Treating it as a side effect of an exclusion script — invisible, uncapped, unreviewed — would put unreviewed deletions into live documents through the one mechanism this design describes as low-risk. That review is mandatory is settled; whether an agent may *perform* the severing autonomously at all remains open below, and the first shipment is scoped accordingly under *Recommended sequencing*.
- **The exclusion machinery has a second, non-destructive use.** It is the mechanism that lets a record be kept in the repository without being kept in the context: committed, versioned, reachable by a human who goes looking, invisible to retrieval. This is what makes an oversized classification record storable (see the consolidation procedure) rather than forcing a choice between a commit message that cannot hold it and a scratch file that discards it. Present exclusion as a general lever for separating *retained* from *retrievable*, not solely as a disposal step.

### Rules vs. skills — the split to encode

These are not alternatives. **Rules prevent accumulation; skills repair what accumulated anyway.** Rules alone leave the pre-existing debt untouched (they do not apply retroactively); skills alone condemn the project to perpetual maintenance.

The assignment criterion is mechanical: a directive belongs in a **rule** if it must apply *always, at zero activation cost*; it belongs in a **skill** if it is a *rare, multi-phase procedure with risk of information loss*; it belongs in a **script or hook** if a shell command could do it.

**Rules** (`CLAUDE.md`, deliberately kept under ~20 lines for this domain — a 300-line `CLAUDE.md` is no longer a rule set, it is documentation the agent dilutes):

- the artifact taxonomy;
- the no-append rule on specs, **stated with its justification** ("history lives in git and in ADRs") — the justification is what makes the agent willing to overwrite;
- the comment policy: only what the code cannot say about itself; no bug-fix references;
- the implicit default: unmarked = current;
- the obligation to **flag rather than rewrite** anything that is no longer verifiable.

**How the taxonomy fits the line budget.** Four artifacts, five rules and two justifications do not fit in ~20 lines if the taxonomy is reproduced with its lifecycle rules. In `CLAUDE.md` the taxonomy is therefore **one line per artifact, function plus a lifecycle keyword only** (state / ephemeral / append-only / state), with a pointer to the project overview for the lifecycle detail. The full table lives in the overview and is not duplicated in the rule set. Treat the line budget as binding and the taxonomy rule as a compressed index, not as an explanation.

**Scope of the justification requirement.** The line budget does not accommodate a justification on every rule, and attaching one to all five would break the budget. Justifications are attached to the **two rules the agent will otherwise rationalize its way around** — the no-append rule and the comment policy — because both ask the agent to destroy information. The remaining three are declarative and self-enforcing. Do not treat "rules carry their justification" as a universal that conflicts with the line budget; treat it as targeted.

**The flag-rather-than-rewrite rule requires an intake, and the intake ships with the rules.** A rule that obliges the agent to flag is inert if there is nowhere for the flag to land: flags accumulate in transcripts, nobody owns them, and within two sessions the rule has trained the agent to produce output that is discarded. The intake is a **convention plus a location** — a single append-only destination for suspected defects, unverifiable statements, and observed obsolete-citation events, with the minimum fields needed to act on an entry (what was observed, where, the originating context — the pass that produced it, or the session in which it was noticed — and the verified-against sha where one exists). It is not a skill and not a rule; it is a file convention and, at most, a script that appends to it.

**The intake's shape is settled; only its path and format are open, and that is deliberately not a blocker.** Read the open question below as a request to *choose* a path and a line-oriented or key-value format in the target toolchain, not as an admission that the intake is undesigned — its destination cardinality (one), its append-only discipline, its three entry kinds, and its required fields are fixed above. Shipping the rules therefore requires a decision that takes minutes, not a design that does not exist. Do not read the sequencing advice further down as blocked on an unresolved question.

**Skills — exactly two.** The division criterion is *not* the artifact type, and it is *not* that one skill deals in local truth while the other deals in external truth — both encounter external truth. It is **what external truth does to the pass**:

1. **Comment consolidation.** What the agent verifies autonomously is **redundancy and obsolescence, against the code, inside the repository**: read the function, compare the comment, delete the regenerable, collapse stacked notes, relocate bug-fix references. But the category the skill exists to *preserve* — an external constraint, an invariant not expressible in the type system — is by definition not verifiable in the repository, so this skill meets tier-3 content routinely rather than exceptionally. For this skill, external truth is a **stop condition**: the unit is frozen byte-for-byte, escalated through the intake, and the pass moves on. It never becomes work the pass has to finish. That is what makes the skill high-volume and largely autonomous — not a local truth source. It may **not** decide autonomously when comment and code disagree; that escalates. Per-file or per-module scope, output verifiable by reading the diff, little human judgment required — **subject to the two-part bound per review unit and to the per-deletion regenerability basis**, without which "verifiable by reading the diff" is a claim rather than a control.
2. **Spec and design-doc consolidation.** Truth source: the code **plus** business rules that live outside the repository, and here external truth is **work to be arbitrated**, not a stop condition. The agent cannot close the loop alone. It produces the exhaustive classification, rewrites what is verifiable, and hands over a `## To be confirmed` section that a person must rule on before the pass completes. Low volume, high risk, human arbitration mandatory.

**Higher automation is not lower risk.** Comment consolidation is the more autonomous skill because external truth stops it rather than blocking it, not because its errors are cheaper. Its characteristic failure — a deleted invariant — is the single most expensive outcome in this whole design, and it is invisible in the resulting document by construction. Do not let the automation gradient be read as a risk gradient in the deliverables; the two skills differ in *who arbitrates* and in *whether arbitration gates completion*, not in *how much a mistake costs*.

**Each skill states its bound, and the bounds are not the same kind of thing.** For comment consolidation the binding constraint is numeric and mechanical: the two-part bound per review unit — removed lines and regenerability-basis entries — enforced at a gate that sees the whole unit rather than resetting per commit. For spec consolidation the binding constraint is the mandatory human arbitration step: the pass cannot complete until a person has ruled on `## To be confirmed`, which limits throughput regardless of file size, and the two-part bound applies on top of it as a review-capacity ceiling. Require each skill definition to name its bound explicitly and to say which kind it is. Do not require the numeric part to be the *primary* bound for both; for the spec skill, presenting it as primary would misdescribe what actually limits the pass.

Merging these two into one skill costs twice: irrelevant instructions get loaded (half the procedure never applies), and — worse — the trigger description becomes generic, so the skill fires when it shouldn't and fails to fire when it should. Trigger precision is the real design constraint of skills. Fragmenting into five has the opposite problem: overlapping triggers, arbitrary selection, and loss of the ability to reason about what was actually done.

**Shared machinery, not duplicated prose.** Both skills face the same scoping problem, and the strategy for solving it must live in **one place both skills invoke** — a target-set selection script over the knowledge graph — not as two prose scoping sections inside two skill definitions. Two prose copies of the same strategy drift, and the drift is silent. The skills differ in what they do with the target set, not in how they choose it.

**Neither rule nor skill** — these are mechanical operations that must not consume a context load to perform what `sed` would do:

- marking a plan `completed` → a merge-checklist step or a hook;
- archiving plans, excluding them from retrieval, and maintaining the inventory that reconciles status marking with physical archiving → a script plus retrieval configuration;
- excluding low-value documents from retrieval (phase one of deletion) → the same script and configuration; the accompanying severance of inbound references is a reviewed destructive edit, not a silent script side effect, per the settled position above;
- target-set selection for both consolidation skills → a single shared script over the knowledge graph, invoked by both;
- **coverage verification of the classification pass** → a script that counts the classifiable units **within the pass's declared scope, as they exist at the verification baseline sha**, according to the unit rule the pass declared, and compares that count against the number of classification entries the agent produced, failing the pass on mismatch. Counting against the working tree at commit time would be incoherent: consolidation removes classifiable units, so the post-rewrite count is guaranteed not to match an exhaustive classification of the pre-rewrite state;
- **cross-checking the declared scope against the target set** → the same script compares the declared scope against the output of the shared target-set selection script, and fails the pass where the declared scope is narrower without a recorded bound-driven split reason. This exists because scope and unit rule are agent-declared, and a control whose parameters the controlled party sets is self-report wearing a script's clothing; the target set is not agent-authored, so it supplies a mechanical floor under the plausibility judgement instead of leaving it entirely to the reviewer;
- **enforcement of the two-part bound** across a consolidation review unit → a check at a gate that observes the whole unit, accumulating removed lines and regenerability-basis entries over it; not agent self-restraint, and not a per-commit counter that resets;
- appending an entry to the escalation intake → a script, invoked by either skill, never a hand-written note in chat;
- updating `last-verified-at` → a side effect of a skill, not a skill, and only on a whole-document pass whose recorded sha is resolvable post-merge, per the settled positions above.

**The coverage check needs a machine-readable input, and the classification record is that input.** The check cannot read a commit message that does not exist yet, and it cannot count entries in prose the agent narrated in chat. The classification is therefore written, during the pass, to a **structured record at a conventional path in a fixed line-oriented or key-value format**, one entry per classifiable unit. That record is the coverage script's input, the source from which the commit message body is rendered, and the thing the human reads alongside the diff. Specify this as a required artifact of the pass with a defined shape; do not specify a format the toolchain has not been observed to support, and mark the format choice and path as open. What must not happen is a coverage check specified against an input that does not exist — that is a control on paper only, and this design has no room for those.

**The record's header declares the four things every check reads.** The review-unit identity, the unit rule, the declared scope, and the verification baseline sha. Each exists because a check would otherwise be undefined: the bound cannot accumulate across a unit it cannot delimit; the coverage count cannot count units without a rule; coverage would fail by construction on every split pass if it were defined against the file rather than the declared scope; and the count would be taken against the wrong tree without a recorded baseline. What remains open is which unit rule is *good*, and how the outstanding remainder of a split file is tracked — not whether the scripts can run. A declared bad rule or an implausibly narrow declared scope is visible to the reviewer and, for scope, partially caught by the target-set cross-check; an undeclared one is neither.

**Required contents of a classification entry.** Each entry carries: the unit reference, the label, and — for any label asserting a fact about the code (`still true`, `obsolete`, `contradicts code`) — the **specific code location or identifier the judgement was verified against**. Deletions on regenerability grounds additionally carry the basis, per the settled position above. This requirement exists because a bare label is producible without reading anything, while a citation is not: it is checkable against the file, and it is what turns a human spot-check of a handful of entries into evidence about the whole pass. Labels alone are not.

**The record is transient in the default path and committed only in the fallback.** In the default path the record is written to the working tree, rendered into the commit message body, and must not be swept into the consolidation commit — a consolidation diff that contains the record is no longer a diff of nothing but consolidation. The mechanism that keeps a transient file out of a commit is toolchain-specific and is marked open below; the operative decision rule is that **where no such mechanism is available, the committed-and-excluded fallback is preferred over risking accidental inclusion**, because the fallback's cost is a retained file nobody retrieves and the alternative's cost is a polluted review unit.

### The consolidation procedure

1. **Isolate the commit.** Consolidation is always a separate commit, never mixed with functional changes. The diff must be readable as a semantic diff, which is what makes it reversible. In the merge-time case this means a separate commit within the same pull request; in the brainstorming-time case it means a standalone commit with no host PR. Concretely: bring the working tree to a clean state first — in the merge-time case by **committing** the functional work, never by stashing it, for the reason given in step 3; in the standalone case by committing or stashing whatever unrelated work is in flight — so that the consolidation diff contains nothing but consolidation. A pass that would exceed either part of the review unit's bound is split into separate review units, not merely into more commits inside the same one.
2. **Scope before classifying, and declare the scope.** Run the shared target-set selection script. Blanket scope is the failure mode, not the safe default. Record the resulting declared scope in the header of the classification record, together with the review-unit identity and the unit rule; where a single file alone would exceed the bound, the declared scope is an explicitly enumerated subset of that file, the split reason is recorded so the target-set cross-check can pass, and the pass does not write `last-verified-at`.
3. **Record the verification baseline.** Capture the sha the pass is being verified against — `HEAD` after step 1's isolation and before any file is read — into the record header. This ordering is not incidental: capturing it before the functional work is committed would record a state the agent never examined, which is also why the functional work must be committed rather than stashed; capturing it after classification would record a state that includes the pass's own writes. It is what the coverage count is taken against, what `last-verified-at` will carry on a whole-document pass, and what makes the pass reproducible either way.
4. **Classify before rewriting.** Pass 1 labels every classifiable unit **in the declared scope** — per the unit rule the record declares — as one of:
   - `still true`
   - `obsolete`
   - `historical decision → ADR`
   - `contradicts code → suspected defect`
   - `not verifiable`

   Write each label, with its unit reference and its required citation or regenerability basis, into the structured classification record described above as the pass proceeds. Only then rewrite. Without this forcing pass, the agent jumps straight to synthesis and that is where loss occurs.
5. **Verify coverage mechanically, and know what the verification does not cover.** Run the coverage-count script against the classification record: classifiable units in the declared scope at the baseline sha in, classification entries out, counts must match; and the declared scope is cross-checked against the target set. Be precise about what this buys: the count check defeats **omission within the declared scope** — the skipped section, the truncated pass — and nothing else. The cross-check raises the floor under scope plausibility but does not establish that the declared scope was *right*, which is why the scope is also stated where a reviewer sees it. Neither defeats **skimming**, because the agent that skims the middle of a long document can still emit one plausible label per unit and pass the count perfectly. Skimming is addressed by the citation requirement in step 4 plus a **human spot-check of a sample of entries against the file**, performed as part of the human review of the review unit and gating its merge: it is cheap, is not producible without having read the unit, and generalizes — entries whose citations do not hold indict the pass, not just the sample. Run all of it. A count-only check reported as coverage evidence is worse than no evidence, because it gets trusted.
6. **The classification record never enters the persisted document.** Its destination is the **body of the consolidation commit message**, which is immutable, outside retrieval, attached to the exact diff it describes, and still available in six months when someone asks what the pass actually looked at. The sole content that crosses from the classification into the document is the `not verifiable` bucket, as the `## To be confirmed` section described in step 9 — items, not the record, and only that bucket. Where the record is too large for a commit message to carry usefully — or where the toolchain cannot reliably keep the transient record out of the consolidation commit — the sanctioned fallback is to commit the structured record as a file that is **excluded from every retrieval channel with its inbound references severed** — retained, versioned, attached to the diff by adjacency, and out of the context; the commit message then carries the counts and a pointer. Uncommitted scratch output or chat output remains acceptable only where neither is practical, with the explicit cost that it discards the coverage evidence immediately after a single use. The size threshold at which the fallback becomes preferable is left open. Rationale for exhaustiveness: if the agent flags only what it believes obsolete, silence becomes ambiguous between "verified, current" and "never examined" — two radically different things the human cannot distinguish. And "never examined" is the common case, because attention over a long document is not uniform: agents work well at the beginning and the end and skim the middle. Exhaustive classification is a forcing function that makes **coverage** visible. The verdict per unit matters less than the guarantee that every unit in scope was looked at.
7. **Verify against the code, not against the document.** Nothing survives unless it is verifiable in the current code or is a genuine decision, constraint, or rationale. The code is the truth about *what it does*; the unique value of documents is the *why* and what was rejected.
8. **`contradicts code → suspected defect` is never resolved by the agent.** The comment or statement is left in place, unmodified, and the divergence is reported — into the escalation intake, not only into the transcript. Rewriting documentation to match code that may itself be wrong is the one failure mode that produces a clean diff and a worse system.
9. **`not verifiable` is the critical bucket.** It is never deleted silently. In a document pass it goes into a `## To be confirmed` section in the document *and* into the escalation intake. That section legitimately belongs in the persisted document, because it represents open work assigned to a person — not metadata. This is the sole exception to the no-per-paragraph-metadata rule, and it is an exception on those grounds specifically. In a comment pass there is no in-file carrier and none is created: the comment is left byte-for-byte unmodified and the escalation travels through the intake and the classification record alone. In either case the freeze applies to the whole declared unit, per the settled position above.
10. **Review the removed lines, not the result.** Reading the final document does not reveal what was lost; reading the `-` lines does. Read them against the classification record: a `-` line with no corresponding entry is a hole the coverage count cannot catch. This step and the entry spot-check in step 5 together constitute the review budget of the unit, and they are the only real control on the regenerability test — which is why the bound in step 1 exists: a diff too large to read, or carrying more independent deletion judgements than a reviewer will actually adjudicate, is a review that did not happen.

### Triggers

Correct:

- completion of a feature or epic (the plan dies; what it taught flows back into the spec);
- **at the start of brainstorming on an area touched in the past** — this grafts onto the existing workflow and yields clean context before the most token-expensive phase, and is the case where the consolidation commit stands alone rather than riding inside a feature PR;
- whenever the agent is observed citing obsolete information — the most reliable diagnostic signal.

Wrong: **mid-implementation. Never.**

**The obsolete-citation trigger is a signal, not an authorization, and the deliverables must say so.** It arrives mid-implementation more often than not, which is precisely where consolidation is prohibited. The resolution: the observation is **recorded into the escalation intake when it happens, and consumed at the next admissible boundary** — feature completion, or the next entry into brainstorming on that area. Observing the signal never licenses an immediate mid-implementation pass, and an intake entry is what stops the signal from being lost while it waits.

Calendar-based triggers are inferior to event-based ones. Doing it "by feel every once in a while" is the worst mode, because information loss happens precisely when no checklist is in play.

### The asymmetry that must be explicit

The naïve two-tier version — "technical details the agent decides, business rules it escalates" — is insufficient, because it hands the agent authority over cases where it can see a fact but not interpret it. Encode **three tiers**:

| Tier | Truth source | Agent authority |
|---|---|---|
| **Code-verifiable** | The code, unambiguously | Decides autonomously. Redundant comments deleted, obsolete statements rewritten, stacked layers collapsed. |
| **Code-visible, intent-ambiguous** | The code shows a divergence, but not which side is correct | **Reports, does not resolve.** A comment/spec statement that contradicts the code is a suspected defect, not a stale document. |
| **External truth** | Business rules, regulation, contracts — outside the repository | **Escalates.** No autonomous deletion under any circumstance. |

The middle tier is the one that gets omitted and the one that causes the most expensive failures. Without the top tier's boundary made explicit, the outcome is technically impeccable consolidations that delete a regulatory constraint nobody had implemented yet — a deletion invisible in review precisely because it is technically correct. Without the middle tier, the outcome is documentation quietly rewritten to describe a bug as intended behavior.

Both lower tiers terminate in the same place: the escalation intake. A tier distinction that does not end in a durable destination is a taxonomy, not a control.

The outer tier is not the rare case. Both skills meet it routinely, and they differ only in what it does to the pass — a stop condition for comments, arbitrable work for specs, per the skill definitions above.

**Present the table with its limitation attached**, per the settled position above: the tiers partition authority, they do not independently verify the judgement that assigns a unit to a tier.

### Critical positions to carry into the project — do not soften these

- **The optimization target is upstream, not downstream.** Reducing after the fact costs far more than not accumulating in the first place. If only one thing gets built, it is append-resistant documents by construction. The consolidation skills are maintenance, not the solution.
- **Many documents should not be compacted — they should be removed from play.** A significant share of documentation in an AI-assisted codebase is write-once, read-never: produced because producing it was cheap. The question to ask of every file is "if this disappeared, what would break?" Aggressive removal returns more than accurate compaction, and costs less. Execute it as retrieval exclusion first and deletion second: the context-cost benefit is captured by exclusion **provided every channel is closed, inbound references included** — an excluded file still linked from a live document is still in play, and in that state the benefit has not been captured and the case for deletion is not answered.
- **The return on comment consolidation is bounded in a way the return on document exclusion is not, and this should temper how it is prioritized.** Excluding a document removes it from retrieval entirely — the tokens are simply never spent. Comments, by contrast, are only ever read as part of a file the agent was going to read anyway, so consolidating them shortens files already in scope rather than removing anything from scope. The saving is real but second-order, while the characteristic failure — a deleted invariant — is first-order. This does not overturn the prediction below that comment debt is the largest and the comment skill the likeliest to be demanded; it does mean the demand should be confirmed by measurement rather than assumed, and that document exclusion is the cheaper first move even where comment debt looks worse.
- **The enemy is not length, it is contradiction.** A long, coherent, true document costs tokens. A short one with three conflicting statements costs correctness — and hours spent working out why the agent implemented the wrong rule. Optimize non-contradiction first, brevity second.
- **Both skills are, first and foremost, scoping problems.** The expensive part is not rewriting; it is deciding which files to work on. Blanket-consolidating a large module is the most reliable way to blow the context window and get a shallow pass through the middle. The target-set selection strategy must be defined before the procedure, must live in shared machinery rather than in each skill's prose, and the existing knowledge graph is the natural instrument for it. This determines whether the skills are usable or merely elegant.
- **Every control in this design must be mechanical or it is not a control.** Coverage checks, the two-part bound, plan status marking, retrieval exclusion: each is a place where the agent's self-report is not evidence. Where a script can verify a claim, the script is mandatory and the claim is not accepted on its own. A control whose input does not exist — a coverage check with nothing to count, an escalation with nowhere to land — is the same failure in a more flattering shape. So is a control whose parameters are supplied by the party being controlled, unless something not agent-authored puts a floor under them.
- **Mechanical is necessary and not sufficient: a check must also measure the property it is credited with.** A well-formed script counting the right number of the wrong thing is more dangerous than no script, because it converts a suspicion into a passing build. Every control in the deliverables therefore states what it verifies **and what it does not** — the count check catches omission within the declared scope and not skimming; the target-set cross-check raises the floor under scope plausibility without establishing that the scope was right; the removed-line cap bounds reading volume and says nothing about whether the removals were correct; the regenerability-entry cap bounds judgement volume and equally says nothing about correctness; `last-verified-at` measures distance from the verified state and not the quality of the verification, is absent rather than approximate after a subset pass, and is absent rather than dangling where the sha would not survive merge; the tier table partitions authority and does not validate tier assignment. Where a control's stated property and its actual property diverge, the divergence is a defect in the design and not a caveat.
- **Human review capacity is a single budget with several claims on it.** The removed-line cap, the regenerability-entry cap, the `-` line reading, and the entry spot-check are not four independent safeguards; they are four demands on the attention of one reviewer in one pass. Any proposal that tightens one by loosening another has not improved the design, and any numeric calibration that sets one without the others is incomplete by construction.
- **Recommended sequencing:** ship the rules first, together with the escalation intake they depend on **and the retrieval-exclusion and plan-archiving machinery**, and build neither skill for roughly two weeks. All three are cheap, non-destructive in their first phase, and independently valuable; the exclusion machinery in particular is the highest return-per-unit-risk item in the design, and withholding it during the observation window would be withholding the intervention most likely to make the skills unnecessary. One scoping caveat is load-bearing and must be stated rather than glossed: phase-one exclusion requires severing inbound references, and whether that is safely agent-executable is open below, so in the first shipment **the severance is performed by a human** while the exclusion configuration itself is scripted. The consequence is that the exclusion benefit accrues at human throughput until that question closes, which qualifies the return-per-unit-risk claim without overturning it — and which makes closing that question the highest-value item on the open list. Rules are the highest value-to-cost intervention and they are *diagnostic* — after two weeks of observation it becomes clear which of the two skills is actually needed and which was imagined for symmetry. Expected outcome (a prediction, worth less than the observation): rules absorb most of the problem on new documents, exclusion absorbs much of the remaining context cost, and the skill actually needed is the comment one, where pre-existing debt is largest and rules do not reach retroactively. **Read this as a prediction about demand, not about safety** — the comment skill is the likeliest to be needed first and simultaneously the one whose failure mode is most expensive, which is why the two-part bound, the per-deletion regenerability basis, and the conservative reading of the regenerability test ship *with* it rather than after it. The observation window is also the window in which the intake produces the first evidence about how often the middle and outer tiers actually fire, and about how often the obsolete-citation signal fires at all; if it produces none, that is a finding about the rules, not a reason to skip the intake.
- **Specified is not scheduled.** Both skills are fully specified in the project knowledge document; only the rules, the intake, and the mechanical machinery are scheduled first. Specifying both is cheap, sharpens the rules by forcing the boundaries to be drawn, and costs nothing as long as neither is built during the observation window. Do not read the sequencing advice as a reason to leave a skill under-specified.
