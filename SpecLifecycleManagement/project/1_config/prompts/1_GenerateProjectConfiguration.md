# Prompt — Generate a Claude Project for Documentation & Spec Lifecycle Management in Spec-Driven Development

---

## Role

Act as a full-stack software engineer with 20+ years of experience, specialized in spec-driven development and in the practical use of generative AI coding agents (Claude Code and equivalents) on large, long-lived production codebases. You have direct experience with the failure modes of AI-assisted documentation at scale. You are opinionated, concise, and you flag disagreement rather than accommodating a premise you think is wrong.

## Task

Produce **three downloadable artifacts** that together configure a Claude Project dedicated to the theme described below. Do not produce a single combined document, and do not deliver the content inline in chat only — each of the three must be a separate downloadable file:

1. **`project-description.txt`** — a synthetic project description in plain text (`.txt`), suitable for pasting into the "What are you trying to achieve?" / project description field when setting up a Claude Project.
2. **`project-overview.md`** — a detailed and exhaustive description of the project in Markdown (`.md`), intended to be uploaded as the primary knowledge document of the project.
3. **`project-instructions.md`** — the project instructions in Markdown (`.md`), intended to be pasted into the Claude Project's custom instructions field, so that every conversation started inside the project inherits the right context, constraints, and behavior.

All three deliverables must be written in **English**.

## Domain Context — read fully before producing anything

### The workflow in use

Every development session follows this sequence:

1. **Brainstorming** — sharing and exploring ideas.
2. **Specification** — writing a design spec / feature spec.
3. **Implementation plan** — the spec is transformed into a detailed development plan.
4. **Implementation** — execution driven by the plan, frequently parallelized across sub-agents.
5. **Code review**, followed by bug fixing and subsequent modifications as needed.

This structure is deliberate and must be preserved. Any recommendation that requires abandoning or restructuring it is out of scope. Interventions graft onto the existing phases; they do not add phases.

**Parallelization is a property of implementation only, and the prohibition on parallelizing consolidation rests on two distinct grounds that must both be stated.** Step 4 parallelizes across sub-agents; consolidation does not.

- **Structural ground — one agent per review unit.** The two-part bound accumulates across a review unit, the coverage count is taken against one declared scope at one baseline sha, and the classification record carries one header. Two concurrent sub-agents working the same review unit produce two baselines, two declared scopes, and two independently-passing bound counters over one unit — which is the evadable-by-arithmetic failure the bound exists to prevent, arriving through concurrency instead of through commit splitting.
- **Capacity ground — concurrency across *distinct* review units is bounded by the reviewer, not by agent availability.** The structural ground alone would permit several agents working disjoint review units in parallel. That is barred separately, because every review unit produced consumes the same single human review budget, and producing units faster than one reviewer absorbs them converts a queue of unreviewed deletions into the default state.

State both grounds. A design that gives only the first invites exactly the workaround the second forbids. Where a pass is too large for one agent, it is **split across review units** (see *the bounds that make diff-based review real*) and those units are **sequenced against review capacity**, not fanned out.

### Assumed environment properties — preconditions, not neutral ground

Three properties of the environment are **preconditions of this design**, not stack-neutral mechanisms. Each must be stated as such in the deliverables, with the consequence of its absence, because a reader who takes the neutrality claim at face value is entitled to conclude the design contradicts itself on nearly every page.

| Precondition | What it must provide | Consequence of absence |
|---|---|---|
| **Version control** | Commit-level diffs, immutable commit identifiers resolvable after the fact, and a review construct that groups commits | Nothing in the design works. Commits, commit messages, pull requests, stashing, merge strategies, and diffs appear throughout as load-bearing mechanisms. |
| **Codebase knowledge graph** | Queryable, rebuildable, with an **observable build state** | The declared-scope cross-check loses its only non-agent-authored floor, and declared scope degrades to self-report. The design still functions; one of its controls does not. |
| **At least two people able to review a consolidation diff** | An author and a reviewer who are not the same person | Inbound-reference severance is unavailable, because self-review of one's own deletions is the self-report failure this design refuses everywhere. Phase-one exclusion is therefore reduced to its configuration half, and the first shipment's headline return is correspondingly lower. |

The third is the one most likely to be silently assumed. State it explicitly: the design's highest return-per-unit-risk item requires two humans, and a single-maintainer project cannot execute it as specified.

### Environment

- Claude Code as the primary coding agent, with a plugin-based workflow (`brainstorm → design spec → implementation plan → sub-agent execution`).
- A codebase knowledge graph built via Tree-sitter plus LLM semantic extraction, used for navigation and orientation, and queryable from the CLI.
- Large, long-lived enterprise codebase; any arbitrary technological stack.
- Significant amounts of accumulated project documentation, in-code comments, specs, implementation plans, and years of revisions and bug-fix history.

**Stack neutrality — and the precise limit of it.** Nothing produced may depend on a specific technological stack. Where this prompt names concrete technologies (.NET, React, TypeScript, SQL, SAP B1, SAP B1 Service Layer, Beckhoff TwinCAT), they are **illustrations of a category** — "an external constraint the code cannot state about itself" — and must be presented as such in the deliverables, never as project facts or as a committed stack. Neutrality is bounded by the three preconditions above and by nothing else.

**Stack neutrality applies to mechanisms, not only to code.** Some interventions below (notably retrieval exclusion, review-unit identification, gate-readability of the classification record, post-merge sha resolvability, and full-text search scoping) are specified as required **capabilities** with named channels but no named tool, because every concrete implementation of them — ignore files, index configuration, glob patterns, graph exclusion lists, search-tool scope configuration, PR-level checks, merge strategies — is toolchain-specific. Where a cost claim or a control depends on such a mechanism existing, the deliverables must state that the claim is conditional on the toolchain providing it, rather than asserting the cost or the control as known.

**The knowledge graph is itself an artifact with a staleness property, and this is load-bearing.** The graph is the instrument of target-set selection and the source of the only non-agent-authored floor under the declared scope for document and comment passes. A cross-check against a stale graph is not a floor — it is a second self-report with an extra hop. The target-set selection script must therefore **record the graph's build state alongside its output**, and the cross-check must **refuse to pass rather than pass silently** when that build state is older than the pass's verification baseline by more than a threshold. The threshold is left open below; that a stale graph invalidates the control rather than weakening it is settled.

**The same staleness requirement generalizes beyond the graph, because not every pass is floored by the graph.** A severance pass is floored on the exclusion inventory, which the graph cannot see. The header field is therefore **the provenance and observation state of whatever floors the declared scope** — the graph's build state for `document` and `comment` passes, the exclusion inventory's last-updated state for `severance` passes — and the staleness check applies to both instances identically. Specifying the field as "graph build state" would leave one of the three declared pass kinds with a mandatory header field that has no referent, which is a design defect and not a detail.

### Who executes what — the constraint stated correctly

All documentation and specification maintenance work is **agent-executed and human-verifiable**: every recommendation must be executable by an agent and verifiable by a human reading a diff. This is a hard constraint on *how work is specified*.

It is **not** a claim that no human performs any step. The table below enumerates the human-executed steps **inside a consolidation pass**; it is not an enumeration of every human act in the design, and the deliverables must say so, because two human acts sit outside a pass entirely and would otherwise look like omissions.

| Human-executed step | Status | Why it cannot be agent-executed |
|---|---|---|
| Arbitration of `## To be confirmed` items — the **ruling**, not its application | **Permanent** | Truth source lies outside the repository; the pass cannot complete without it. |
| Review of removed lines plus the entry spot-check | **Permanent** | It is the only control on the regenerability test; an agent reviewing its own deletions is the self-report failure this design refuses everywhere. |
| Severance of inbound references | **First shipment only** | Whether it is safely agent-executable is an open question below; until it closes, a human performs it. Its review is permanently human and permanently non-authorial. |

The first two are not exceptions to the constraint — they are *the verification half of it*. Only the third is a scoping concession, and it is temporary.

**Two human acts sit outside any pass and are not carve-outs from the constraint.** First, **observing an agent citing obsolete information** and recording it in the escalation intake: this happens in session, mid-implementation, and is an observation rather than a step of a pass. Second, **deciding phase two of an exclusion**, where a miss signal has been defined. Enumerate both alongside the table rather than leaving them to be discovered as unaccounted human work.

**Arbitration produces a ruling; a subsequent agent-executed pass applies it — and the original framing left this executor undefined.** When a person rules on a `## To be confirmed` item, they record the ruling and its **ruling sha** in the intake and set the entry's state; they do not perform the resulting edit. The edit — a sentence into the body, a relocation to an ADR, or a deletion — is performed by a later agent-executed pass carrying its own record, baseline, coverage check, and bound, exactly like any other pass. This matters for two reasons. It keeps the design's most important bucket from having an unnamed executor, and it gives that later pass a **non-agent-authored authority** for its removal: the intake entry, cited in the classification entry. Without this, the resolution of the highest-risk bucket in the design is either unowned or performed by a human outside every control the design specifies.

### The observed problem

On a large codebase with heavy documentation history, AI agents asked to change a business rule, a spec, or a comment consistently **append a revision** instead of **editing the existing content**. They add "Revision 3", "Update 2026-07-14", stacked layers of historical notes, and references to old bug fixes.

This has real upside: history is preserved, past problems remain traceable, and context is richer. But it also:

- inflates token consumption and fills the context window;
- injects obsolete and outdated information into the working context;
- produces documents in which multiple statements contradict each other, with no ordering signal telling the agent which one is current;
- makes the eventual consolidation pass increasingly expensive and increasingly risky.

The need is therefore **periodic consolidation**: collapsing accumulated revisions into a single, complete, current, non-contradictory statement of the truth — across project documentation, specs, implementation plans, and in-code comments — without silently losing information that still matters.

### Diagnosis to encode in the project

The append behavior is not a defect; it is a rational response to an incentive. Deleting information requires knowledge the agent does not have (*is this still true? does anything depend on it?*), while appending is always safe — it never loses anything, and the cost it imposes is paid later, by someone else, in a different session. Unless a document explicitly states where history lives, the agent assumes history lives in that document and preserves it.

A practical consequence: instructing agents to "be concise" or "avoid redundancy" does not fix this, because it does not change the incentive. Changing the incentive means telling the agent, in the artifact itself, where history belongs instead.

The root cause is that documents are performing two incompatible functions simultaneously: **describing current state** and **recording history**. These have opposite lifecycles — the first must be rewritten, the second is immutable by definition. Keeping both in the same file guarantees accumulation.

### Units of account — fix these three terms before anything else

Several bounds and checks below are scoped to one of three units, and the design is unreadable if they are conflated. Define all three in the deliverables.

**The review unit.** Everything a single human review pass is expected to read **as consolidation**:

- in the merge-time case, **the set of consolidation-class commits within one pull request** — the realignment commit, the inbound-reference severance commit where one is present, and the record commit where the committed-record channel is used;
- in the brainstorming-time case, the standalone commit or commit set constituting one consolidation pass.

Commits subdivide a review unit for readability; they do not create additional review capacity. Because bounds are enforced against it, a review unit must carry an identity a script can read: the enforcement mechanism cannot accumulate across a unit it cannot delimit. The identity is declared in the header of the classification record, alongside the pass kind, the unit rule, the declared scope, the baseline, and the floor provenance; the concrete mechanism that surfaces it to the gate is toolchain-specific and left open below.

**Commit ordering inside a review unit is fixed at both ends, because the ancestry check is otherwise ambiguous.** The gate verifies that the declared baseline is the parent of the first consolidation-class commit in the unit — and the record commit is consolidation-class for identity purposes, so without an ordering rule the check has two possible subjects. The rule: **the baseline's child is the first commit that removes content** (the realignment commit, or the severance commit where the unit contains only severance). The record commit is never first. Where both realignment and severance are present in one unit, the realignment precedes the severance. State this; an ancestry check with an ambiguous subject is not a check.

**The review unit is not the whole of what the reviewer reads, and the design must say so rather than quietly assume otherwise.** In the merge-time case the same person, in the same sitting, also reads the functional diff. The consolidation bound governs the consolidation commits alone, so a bound-compliant realignment attached to a large functional change still exhausts the reviewer — and the single-budget position is violated by a design that notices only half the load. Four consequences, all settled:

- the functional diff's volume is **not** counted against the consolidation bound (they are different judgements, and mixing them would make the cap unreadable);
- a pull request whose functional diff is itself large **moves its realignment out** — the realignment becomes a standalone pass under the no-host-PR case rather than riding along. What counts as "large" is a threshold, calibrated with the rest of the review budget rather than invented; it is named among the open questions;
- where a realignment does ride along, the consolidation volume admissible in that unit is the **residual** budget after the functional diff, not the full cap. This matters at exactly one place in the design — the split of an oversized realignment, below — and stating it is what stops "the portion that fits" from being computed against a denominator the reviewer does not actually have;
- **the residual is defined against the line half of the bound and not against the judgement half**, because a functional diff consumes reading attention while emitting none of the removal judgements the judgement cap counts. Do not silently apply a residual to a quantity the functional diff does not produce, and do not conclude from this that the functional diff's own review judgements are free: the control that actually covers that case is the functional-diff threshold above, which moves the realignment out entirely. Whether the judgement half should carry a residual of its own is a calibration input, named among the open questions.

**The declared scope of a pass.** The set of classifiable units the pass commits to examining — normally a set of whole files, and, where a single file alone would exceed the bounds of a review unit, an explicitly enumerated subset of one file. It is stated in the header of the classification record alongside the declared unit rule, and it is what the coverage check counts against. Coverage is a claim about the declared scope, never about the file system.

**Relocation targets are outputs of a pass, not members of its declared scope.** An ADR written or extended by a `historical decision → ADR` disposition is not classified, is not counted for coverage, and does not exist at the baseline sha the count is taken against. Its added lines fall under the accepted asymmetry that caps govern removals and not additions. State this, because a declared scope that silently included its own outputs would fail coverage by construction on every pass that relocates anything.

**The classifiable unit.** The smallest thing a classification entry refers to. It has no *global* definition, because document structures differ and source files differ from prose; it is fixed **per pass** by the unit rule the pass declares in its record header.

Three properties of the unit rule are settled, and the design does not work without any of them:

- **The rule is drawn from a closed, machine-evaluable set, not written freely.** The coverage check counts classifiable units according to the declared rule; a script can only count under a rule it can evaluate. "The declared rule makes the check implementable regardless of which rule is chosen" is false for a free-form rule, and the deliverables must not repeat it. The requirement is therefore: the toolchain publishes a **closed enumeration of supported unit rules**, each with a counting implementation, and a pass declares one of them by name. Illustratively — and these are illustrations of the *category*, not a fixed list — a Markdown block-level element, a comment block, a single comment line, a numbered list item.
- **The enumeration must contain at least one rule for every pass kind the design defines.** A severance pass's unit rule is "one inbound reference occurrence"; if that is not a member of the enumeration with a counting implementation, the severance pass cannot declare a rule the gate can evaluate, and its coverage check does not exist. Which further rules the enumeration should contain is open below; that it must cover all three pass kinds is not.
- **Choosing the rule is a review-budget decision, not a free per-pass preference.** A coarse rule reduces entry count, reduces spot-check surface, and freezes more redundancy along with frozen content; a fine rule recovers those deletions and raises entry count, removal-judgement count, and spot-check surface — all of which draw on the single review budget. The trade-off is therefore constrained on both sides and must be presented as coupled to the budget rather than as a knob the pass turns at will.

### Artifact taxonomy (the primary intervention)

| Artifact | Function | Lifecycle |
|---|---|---|
| Spec / design doc | **State** | Present tense, describes the system as it is now. No "Revision N" sections. When a business rule changes, the sentence changes. Re-aligned to reality at merge time, not only before implementation. |
| Implementation plan | **Ephemeral** | Has a death date. Marked `status: completed` mechanically at merge; archived later at the author's discretion; **excluded from all retrieval channels** once archived — indexes, globs, knowledge graph, unrestricted full-text search of the tree, **and inbound references from surviving documents**. |
| ADR | **Append-only log** | One file per decision. **The body is immutable; `status` is the single mutable field** — `accepted \| superseded-by ADR-NNN`. All historical rationale that currently pollutes specs belongs here. |
| Code comments | **State** | Explain why the code is the way it is *now*. Never "fix for bug #1234" — that is a commit message, already in git. |

**The ADR immutability carve-out is explicit because the two properties collide.** An artifact cannot be immutable and carry a status field that changes on supersession. The resolution: the body — the decision, the context, the rationale, the consequences — is never edited; the `status` field is the one line the supersession step rewrites, and that rewrite is a mechanical operation, not a consolidation. State the carve-out rather than leaving a reader to discover that the taxonomy's own row contradicts itself.

**Mechanical status marking is exempt from the separate-commit rule — for plans and for ADRs alike.** Marking a plan `completed`, and rewriting an ADR's `status` on supersession, remove nothing, require no judgement, and produce one-line diffs. Applying the consolidation isolation rule to either would be ceremony. State the exemption for both, not only for plans: the isolation rule governs edits that **remove content on the strength of a judgement**, and mechanical status marking is neither.

**Reconciliation of merge-time realignment with the separate-commit rule.** "Re-aligned to reality at merge time" and "consolidation is always a separate commit, never mixed with functional changes" are reconciled as follows: the realignment is **a separate commit inside the same pull request** as the functional change. Same PR, distinct commit, independently readable diff. State this resolution explicitly in the deliverables rather than leaving the reader to infer it.

**Consolidation without a host PR.** The merge-time case is not the only one. A consolidation triggered at the start of brainstorming (see *Triggers*) has no functional change to accompany and therefore no host pull request; it stands alone as its own commit and, where the workflow requires review, its own pull request. The invariant is *never mixed with functional changes*, not *always inside a feature PR*. Say this explicitly, because the same-PR reconciliation above otherwise reads as a requirement to find a host PR that does not exist.

**An oversized merge-time realignment cannot satisfy both rules unchanged, and the resolution has a cost that must be stated.** A pass exceeding either part of the bound is split across review units; a review unit in the merge-time case lives inside one pull request; therefore an oversized realignment cannot all ride in the host PR. The resolution: **the portion that fits — measured against the residual budget after the functional diff, not against the full cap — rides in the host PR as its own commit, and the remainder becomes one or more standalone passes.** The cost, which the deliverables must state rather than gloss: the spec is knowingly left **partially realigned** to code that has already merged, and — per the subset-pass rule — carries **no verification marker** in the interim. Tracking that outstanding remainder is an open question below. Do not resolve this by raising the bound, and do not resolve it by mixing the realignment into the functional commit.

### Positions already settled — treat these as decided, do not re-litigate

#### On comments and the regenerability test

- The source of truth about *what the system does* is **the code itself**, not the comments. Comments can lie, and are the only artifact in the repository that can lie without immediate consequence — no test breaks. Comments must therefore be **compacted, not annotated**: they should carry only current truth.
- The operational rule for comments is not "keep comments true" but **"reduce the surface of what can lie."** A comment that restates the code must be **deleted, not compacted** — it adds nothing and can diverge. This category is large in AI-assisted codebases, because models comment generously by default.
- The bright line for "restates the code" is **regenerability**: if the comment could be reconstructed from the signature, the identifiers, and the control flow alone, it is redundant and is deleted. If reconstructing it would require knowing something not present in the file, it is not redundant, however obvious it looks. This test exists because "looks redundant" is exactly where an LLM misjudges — a one-line comment stating an invariant reads like a restatement.
- **The test must name its reconstructor, because the answer changes with it, and the reconstructor is not the agent.** "Reconstructible from signature, identifiers, and control flow" describes something an LLM holding the whole knowledge graph can do cheaply and a human cannot. The standard is therefore fixed as: **a competent engineer unfamiliar with this module, reading only this file, with no graph and no search.** Not the agent performing the pass; not a reader with repository-wide context. Without this fixed, the test silently optimizes the repository for the agent and degrades it for the person paged at 02:00 — and the deletion is invisible in review because the reviewer, who does have context, can also reconstruct it.
- **The conservative reconstructor shrinks the comment skill's expected yield, and the deliverables must say so rather than let the skill be sold on volume.** Under this standard, most comments in a codebase with mediocre naming are *not* regenerable, so the deletion authority the skill exercises collapses toward the trivially tautological. This is the correct outcome — the asymmetry below demands it — but it is also a prediction about return that belongs next to the prediction about demand, and it is one of the things the observation window should confirm or falsify.
- **The regenerability test is scoped to comments and is not extended to prose, and this is a deliberate limit with a stated cost.** The reconstructor standard was fixed for a reader of a source file; there is no equivalent standard for a specification, and inventing one would extend the design's weakest judgement to its highest-value artifact. The removal grounds available to a document pass are therefore `obsolete`, `historical decision → ADR`, and `resolved-already-actioned` only. The cost, which must be stated: a verbose-but-true spec is not shortened by consolidation. It is shortened by rewriting the statements that are actually false, or removed from play by exclusion — which is consistent with the position that the enemy is contradiction rather than length, and with the position that exclusion returns more than compaction.
- **Every deletion made on regenerability grounds records its basis.** The classification entry for a deleted comment names what reconstructs it — which signature, which identifiers, which control-flow structure — **and does so against the reconstructor standard above**. This costs one clause per entry and converts the weakest link in the design from an unexaminable judgement into a spot-checkable claim: a reviewer can read the basis and the `-` line together and disagree. An entry whose basis amounts to restating the comment is not a basis and fails review.
- Only comments carrying what the code cannot say about itself survive: the reason for a non-obvious choice, an external constraint (illustratively: SAP B1 / Service Layer behavior, a TwinCAT quirk), a rejected alternative and why, an invariant not expressible in the type system. This category must be **defended conservatively** during consolidation. The failure modes are asymmetric: keeping one redundant line costs tokens, deleting one genuine invariant costs a defect.
- Historical bug-fix references in comments are not to be compacted but **relocated** — to a commit message or an ADR.
- **A comment that disagrees with the code is not automatically a stale comment.** The agent can observe divergence; it cannot determine which side is wrong, because it cannot distinguish intended behavior from a defect. Divergence is therefore **escalated as a suspected defect**, never silently resolved by rewriting the comment to match the code. Without this rule, the comment-consolidation skill launders bugs into documentation, and the laundering is invisible in review precisely because the resulting comment is accurate about the code.
- **In a code-comment pass, the `not verifiable` bucket has no in-file carrier, and none is to be invented.** A source file has no front matter and no place for a `## To be confirmed` section, and per-comment meta-annotation is prohibited outright. The resolution: a comment classified `not verifiable` is **left in place, byte-for-byte unmodified**, and the escalation travels entirely through the out-of-file channels — the classification record for the pass and the escalation intake below. This is a deliberate asymmetry with document passes, where the same bucket lands in a `## To be confirmed` section visible to the next reader of the file. Its consequence is that an unverifiable comment is invisible to anyone who opens the file, which weakens escalation for the very skill most likely to run first; that consequence is recorded as an open question rather than patched with an annotation.
- **The intake, not the file, is what gives a comment pass memory, and this is what makes repeated passes idempotent.** Because a frozen comment carries no marker, a later pass over the same file re-encounters it, re-judges it, and — absent a rule — re-escalates it. The rule: the escalation step **reads before it appends**, and an entry is appended only where no entry in a suppressing state already exists for the same unit reference. Without this, the intake accumulates duplicates proportional to how many times a file has been passed over, and the observation window's first evidence about how often the outer tier fires is inflated by re-runs rather than measuring anything.
- **Read-before-append is inert without a churn-stable unit reference, and this is a hard requirement rather than a detail.** Unit references are structural or positional — block *N*, comment line *N*, a heading path. Consolidation itself shifts them, and so does every unrelated edit to the file. A dedup key built on a reference that moves will both fail to suppress genuine duplicates and falsely suppress new observations about different content. The intake's unit reference must therefore be **stable under file churn** — anchored to content or to a durable identifier rather than to position — and the deliverables must state that requirement even though the concrete scheme is toolchain-specific and open below. This is load-bearing: the intake is the design's only memory, and an intake whose keys drift has no memory at all.
- **Freezing happens at the declared unit, and it applies to both frozen dispositions.** A unit labelled `not verifiable` **or** `contradicts code → suspected defect` is preserved whole, including any regenerable lines inside it; the pass does not reach into a frozen unit to compact part of it. A coarse unit rule therefore freezes redundancy along with the frozen content. A pass that needs finer resolution declares a finer unit rule — a single comment line rather than a block — and accepts the higher entry count and the larger spot-check surface that follows, which is a claim on the review budget rather than a free choice. Do not present the freeze as a defect to be engineered around: it resolves in the cheap direction of the standing asymmetry, since a frozen redundant line costs tokens while reaching into a frozen unit risks the deletion the label exists to prevent.

#### On the classification dispositions themselves

- **Exactly one disposition per classifiable unit, because the coverage count depends on it.** A count of entries against a count of units is only meaningful if the mapping is one-to-one.
- **The disposition set has seven members for content passes, and a disjoint two-member set for severance passes.** The earlier five-label set was incomplete in two ways that broke other parts of the design, and both gaps must be closed rather than papered over. It had no disposition for a comment deleted on regenerability grounds — so the judgement cap had to name "entries recording a regenerability deletion" as a third countable thing corresponding to no label — and it had no disposition for an item a person had already ruled on, so the exemption of such removals from the judgement cap attached to nothing.

| Disposition | Applies to | Effect | Judgement cap | Requires |
|---|---|---|---|---|
| `resolved-already-actioned` | document passes | Removed | **Zero** | Citation of the intake entry and its ruling sha |
| `contradicts code → suspected defect` | all content passes | Frozen whole, escalated | Zero | Code citation |
| `not verifiable` | all content passes | Frozen whole, escalated | Zero | — |
| `historical decision → ADR` | all content passes | Relocated | Counts, weight open | — |
| `obsolete` | all content passes | Removed | Counts, unit weight | Code citation |
| `regenerable → delete` | **comment passes only** | Removed | Counts, unit weight | Regenerability basis against the reconstructor standard |
| `still true` | all content passes | Retained | Zero | Code citation |
| `severed` | **severance passes only** | Reference removed | Counts, unit weight | The exclusion-inventory entry for the target |
| `retained` | **severance passes only** | Reference kept | Zero | Reason |

- **`still true` and `regenerable → delete` are defined to be disjoint, which is what keeps the precedence order coherent.** `still true` means *verifiable in the current code and not reconstructible under the reconstructor standard* — therefore retained. `regenerable → delete` means *verifiable and reconstructible* — therefore removed. Defined loosely, every regenerable comment would also satisfy `still true`, and a precedence order that resolves upward would make the delete disposition unreachable. State the definitions, not just the names.
- **A severance pass needs both of its dispositions, or its coverage check is unfalsifiable.** If every entry is a severance, entry count equals occurrence count by construction and the check verifies nothing. `retained` exists so that a decision *not* to sever a particular occurrence is recorded, counted for coverage, and visible to the reviewer with its reason.
- **A unit can genuinely satisfy more than one disposition, so a precedence order is mandatory rather than a nicety.** A stacked revision note is both obsolete as state and historically meaningful; a contradicting statement may also be unverifiable. Absent a tie-break, the disposition is whichever the agent happened to reach first, and the classification becomes non-reproducible while the count keeps passing.
- **The order runs from most conservative to least, and the first match wins:**
  `resolved-already-actioned` **>** `contradicts code → suspected defect` **>** `not verifiable` **>** `historical decision → ADR` **>** `obsolete` **>** `regenerable → delete` **>** `still true` (disjoint from the preceding entry by definition).
  Evidence before judgement, freeze before escalate, escalate before relocate, relocate before delete. State the order and state its rationale: every step down the list transfers more authority to the agent, so the tie-break must resolve upward — and `resolved-already-actioned` sits at the top precisely because it transfers *no* authority to the agent, the authority having come from a recorded human ruling. The agent may apply it **only** where an intake entry in state `resolved-actioned` exists for that unit; without that evidence the disposition is unavailable and the unit is classified on its merits.
- **The precedence order deliberately over-reports into the suspected-defect channel, and the intake must be able to absorb that.** A unit that is both unverifiable and apparently divergent from the code is labelled a suspected defect, even though the agent cannot establish that the statement is wrong rather than merely unconfirmable. This is the right resolution — it resolves upward — but it routes arbitration requests into the channel with the most expensive consumer. The consequence, which is settled: the intake supports **reclassification of an open entry between kinds by its consumer**, and a reclassification updates the existing entry rather than appending a new one.

#### On the `## To be confirmed` section — its grounds, and its lifecycle

- **The exception is on state-versus-open-work grounds, not on metadata grounds, and getting this right matters downstream.** A `## To be confirmed` section is not per-paragraph verification metadata and does not violate that prohibition at all; calling it "the sole exception to the no-per-paragraph-metadata rule" is a category error that muddles the very distinction the open question about in-file comment markers has to rule on. The rule it genuinely excepts is *documents describe current state only*: open work assigned to a person is not current state, and it earns its place in the file because the next reader must see it. State the grounds this way.
- **The section is open work, and open work is resolved by deletion.** A person rules on an item, and the item then either becomes a sentence in the body (it was true), moves to an ADR (it was a decision), or disappears (it was neither). It is never re-labelled, never annotated with its resolution, and never kept as a record of having once been uncertain — that record is the intake entry and the commit message.
- **A subsequent pass over the same document treats existing items as classifiable units, with a defined disposition in both cases rather than one.** An unresolved item is `not verifiable` and frozen; the pass appends nothing to the intake where a suppressing entry already exists. An item whose intake entry is in state `resolved-actioned` is `resolved-already-actioned` and removed: its removed lines count against the line cap, and it contributes **zero** to the judgement cap, because nobody is being asked to accept the agent's reasoning — only to observe that a person already ruled, which the entry's citation of the ruling sha makes checkable. Stating both dispositions matters: the earlier framing named the label for the unresolved case only, and exempted the resolved case from the judgement cap without naming a label the exemption could attach to.
- **A statement ruled true-but-unconfirmable in the repository would otherwise loop forever, and the intake's terminal states are what break the loop.** A person rules an item true; it becomes a sentence in the body; the next pass classifies that sentence `not verifiable` and returns it to the section. Since the design forbids per-paragraph metadata, nothing in the file can record that a ruling was made — so the suppression must live in the intake. Entry states are therefore three, not two: `open`, `resolved-actioned`, and `resolved-confirmed-external`. The last is terminal and **suppresses re-escalation of the same unit indefinitely**, which is what makes repeated passes over genuinely external content converge instead of oscillating. Without it, the intake's open set grows monotonically with the amount of legitimate tier-3 content in the repository, and the first evidence about how often the outer tier fires is dominated by permanent residents.
- **Suppression lapses when the content changes, and this is correct rather than a leak to be plugged.** Because the unit reference is churn-stable by being anchored to content, editing the statement produces a new reference and the suppression no longer matches. State this as an accepted property with its rationale — a changed statement is a new statement and deserves a fresh ruling — because the alternative fix, anchoring the reference to position, destroys the dedup key the intake depends on.
- **A section that survives several passes unresolved is a finding about the intake's consumer, not a reason to let it grow.** The design's one sanctioned in-document carrier is the one place the append pathology can reappear, and it reappears exactly when nobody is consuming the intake. Say so, and treat the growth as the signal it is.
- **The caps govern removals, not additions, and this asymmetry is accepted deliberately rather than by omission.** Items added to a `## To be confirmed` section are added lines a reviewer must read, and no cap governs them. The same applies to lines added to a relocation target. The design accepts this on the grounds that each item is open work assigned to a person and that unresolved growth is itself the diagnostic signal above. State the asymmetry explicitly, because leaving it unstated makes the one place the pathology can return look like the one place nothing was thought about; whether added-line volume needs its own ceiling is open below.

#### On the bounds that make diff-based review real

- **Because the regenerability test is the weakest link, the volume it is applied to must be bounded.** The test is fallible in exactly the direction that costs a defect, and the only control on it is a human reading `-` lines. A consolidation whose removed content exceeds what a reviewer will actually read has no control at all — the diff-based review guarantee is nominal.
- **The bound on a consolidation review unit has two parts, because two different things exhaust the reviewer.** Reading volume is exhausted by removed lines; judgement volume is exhausted by the number of independent removal judgements the reviewer must be willing to accept. These do not move together: one forty-line removed block is one judgement, while forty removed one-line comments are forty, and a line-only cap treats them as equivalent. Every consolidation review unit therefore carries **both** a cap on removed lines **and** a cap on independent removal judgements. A pass may breach neither. Both numeric values are to be calibrated by observation and must not be invented in the deliverables.
- **Call it a removal-judgement cap, not a deletion-judgement cap, and define its countable set once against the disposition table.** The countable set is: **`obsolete`, `historical decision → ADR`, `regenerable → delete`, and `severed`.** It excludes the two frozen dispositions, `still true`, `retained`, and `resolved-already-actioned` — the last because its authority is a recorded human ruling rather than an agent judgement. Defining the cap against the regenerability basis alone would make it bind on comment passes and go nearly slack on prose passes, where removals are authorized by an `obsolete` disposition and carry no regenerability basis at all — leaving judgement volume effectively unbounded in exactly the pass type where a single deleted paragraph can cost the most.
- **An ADR relocation is counted, and it is not counted at a discount.** Verifying a relocation requires the reviewer to read two diffs — the removal from the source and the addition to the ADR — and to judge the transfer faithful. It therefore costs *more* reviewer attention than a plain deletion, not less. Do not present relocation as the cheap case; whether it should carry more than unit weight in the cap is a calibration input.
- **Both parts of the bound are scoped to the review unit, not to the commit, and splitting does not raise them.** Review capacity is a property of the human reading the pass, so a bound enforced per commit is evadable by arithmetic: four commits of two hundred removed lines each satisfy a two-hundred-line per-commit cap and still present the reviewer with eight hundred lines. A pass that would exceed either part is therefore **split across review units** — separate PRs, or separate passes on separate days — not across more commits inside the same one, and not across concurrent sub-agents. Subdividing into multiple commits within a review unit remains encouraged for diff readability and remains subject to the same totals.
- **Every consolidation-class commit in the unit counts against the totals, including the severance commit.** Inbound-reference severance removes lines from live documents on the strength of a judgement, so it is consolidation for the purposes of the cap. A design that exempted it would let the one mechanism it calls low-risk carry unbounded deletions.
- **A record commit is consolidation-class for identity and contributes zero to both caps.** Where the committed-record channel is used, the record file is committed **in its own commit inside the review unit**, never inside the consolidation commit — otherwise the consolidation diff contains something other than consolidation, which is the property that makes it reviewable. The record commit removes nothing and authorizes nothing, so it adds no lines to the removal cap and no entries to the judgement cap. State this, or the requirement to keep the record out of the consolidation commit and the requirement to materialize it inside the review unit read as mutually exclusive.
- **The bound applies to every consolidation review unit, not only to comment passes.** Its justification is review capacity, and review capacity is a property of the human, not of the artifact type: a spec consolidation that removes eight hundred lines is exactly as unreviewable as a comment consolidation that removes eight hundred lines. Whether the *numeric values* should differ by pass type — removed prose, removed comment lines, and removed reference occurrences are not equally dense — is deliberately left open below. The bound is a review-capacity constraint, not a quality metric.
- **The bound and the spot-check draw on the same budget and are calibrated as one decision.** The deliverables must present the review budget of a unit as **one quantity with four claims on it** — removed lines to be read, removal judgements to be accepted, entries to be spot-checked, and, in the merge-time case, the functional diff sharing the same sitting — and must state that the numbers are calibrated together or not at all.
- **The bound's two halves are gated at different times, and the ordering exception is narrower than it first appears.** Three statements are settled and must all be made:
  - **The judgement half is a pre-rewrite gate.** The removal-authorizing entry count is known at the end of classification and does not depend on the rewrite.
  - **The line half admits a pre-rewrite *projection* and a post-rewrite *measurement*.** The sum of the lines of all removal-authorizing units at the baseline is a computable **upper bound** on removed lines before any file is written. Because it is an upper bound and not the value, exceeding it is a **re-scope decision surfaced to the author**, not an automatic failure; the measured count after the rewrite is the gate. Stating this shrinks the design's one ordering exception from "the line half is post-hoc" to "the line half's exact value is post-hoc", and it stops the common case of discovering an oversized pass only after paying for the rewrite.
  - **On failure of the post-rewrite measurement, the admissible remedies are enumerated in advance** — split the pass across review units and re-run, or discard and re-scope — and *raising the cap, redistributing across more commits inside the same unit, and fanning out across agents are not among them.*
- **Both halves are re-checked at the review-unit gate, and the pre-rewrite checks do not substitute for that.** A pre-rewrite judgement check reads a record in the author's working tree; it is a cheap local gate whose purpose is to fail before the rewrite is paid for. It is not a control, because its input is not visible to anything but the author. The gate that observes the whole review unit re-checks the judgement half and the line half against the **materialized** record. Say this, or the design ships its judgement cap as a self-administered check with nothing behind it — which is the failure it refuses everywhere else.
- **Enforcement must run at a gate that can see the whole review unit.** A pre-commit hook cannot see a pull request, so in the merge-time case a pre-commit hook is insufficient by construction: it can only ever enforce a per-commit total, which is the evadable bound this design rejects. Enforcement therefore runs at whatever gate observes the complete unit — a PR-level check in the merge-time case, a pass-level check reading the review-unit identity from the classification record header in the standalone case. Specify the requirement; the concrete gate is toolchain-specific and left open below.
- **A gate can only read committed content, so the record must exist in a gate-readable form inside the review unit.** This is the hinge that makes the mechanical checks real rather than nominal. Every pass must materialize the record inside its review unit through **one of exactly two channels**:
  1. **rendered into the commit message body in a fixed machine-readable format** — which makes that body a parsed contract, not merely human-readable prose, and constrains the format accordingly; or
  2. **committed as a file that is excluded from every retrieval channel** (see *On retrieval exclusion and deletion*), in its own commit within the review unit.
  Which of the two a given toolchain supports is left open below. That one of them is mandatory is settled, and a pass that materializes neither has no enforceable bound and no gate-verified coverage, whatever it claims.
- **The gate recomputes what it can, and the deliverables must state precisely what it cannot.** Asserting "the gate recomputes; it does not read the agent's arithmetic" as a universal is false, and the falsehood matters because it would credit the judgement cap with a floor it does not have.
  - **Recomputable from the repository and the diff:** the classifiable-unit count within the declared scope at the declared baseline under the declared unit rule; the removed-line count; the baseline's ancestry; the declared scope against a non-narrated target set.
  - **Not recomputable:** the removal-judgement count, because it is derived from dispositions the agent wrote. No script can independently determine that a removed paragraph was genuinely `obsolete` rather than mislabelled to keep the count down.
  - **What floors the non-recomputable half:** the coverage check (every unit in scope carries exactly one disposition), the **removal-authorization coverage check** below, and the human spot-check. State the residual exposure plainly: a pass can under-count judgements by mislabelling a removal, and the control on that is a reviewer reading `-` lines against the record.
- **Removal-authorization coverage is a mechanical check and should not be left as a human observation.** Every removed line in a consolidation-class commit must fall within a classifiable unit whose entry carries a removal-authorizing disposition (`resolved-already-actioned`, `historical decision → ADR`, `obsolete`, `regenerable → delete`, `severed`). A removed line with no entry is an unrecorded removal; a removed line inside a unit whose entry is `still true`, `retained`, or frozen is a mislabelling. Both fail the gate. This converts the reviewer's instruction to notice a `-` line with no corresponding entry into a script, and it is the strongest available floor under a count the gate cannot recompute.
- **The declared baseline sha needs its own floor, or the whole count is taken against a state of the agent's choosing.** The gate verifies that the declared baseline **is an ancestor of the review unit's consolidation-class commits and is the parent of the first commit in the unit that removes content** — which in the merge-time case is the functional commit, exactly as the isolation ordering requires. A baseline that fails this test invalidates the pass; it is not a warning.
- **The target set the cross-check compares against must not arrive by way of the agent's narration.** The target-set selection script's output — together with the floor's provenance and observation state — is therefore either **committed inside the review unit** alongside the record, or **re-run by the gate itself**. Which of the two a toolchain should prefer is open; that the compared-against side must be non-agent-authored is settled, since that is the entire basis on which the cross-check is credited as a floor.
- **The scope cross-check fails in both directions, and its admissible narrowing reasons are enumerated rather than left to interpretation.** It fails where the declared scope is **broader** than the target set, since blanket scope is the named failure mode and an uncaught expansion is how a pass acquires it. It fails where the declared scope is **narrower** unless the header records one of exactly two reasons: a **bound-driven split**, or a **freshness exclusion** — a target-set member omitted because its `last-verified-at` is close enough to the baseline that re-verifying it would spend review budget for nothing. Enumerating the second matters: without it, the only compliant response to a partly-fresh target set is to declare it all in scope and pay to re-verify, which the single-budget position forbids.
- **The three tiers are a partition of authority, not an independent control on the regenerability test.** Tier assignment is itself a judgement the agent makes before it knows the answer: it cannot know a comment states external truth until it has already decided the comment is not regenerable. A deleted regulatory constraint *is* a tier-3 item misclassified as tier-1, so the tier table cannot be presented as the safety net that catches regenerability errors — it is the same judgement wearing different labels. The only controls genuinely independent of that judgement are the two-part bound, the removal-authorization coverage check, and the citation-plus-spot-check. State this in the deliverables wherever the tier table appears, or the table will be read as protection it does not provide.

#### On plans

- Implementation plans are **archived, not deleted** — but archived plans must be invisible to retrieval. A readable archived plan is worse than a deleted one: it carries the authority of a spec and the content of an intention.
- Plan status marking (`completed`) happens **at merge, immediately**; physical archiving happens **later, at the author's discretion**. These two events are deliberately decoupled. The reason: between merge and archiving, a live plan saying "I will do X" coexists with a spec saying "the system does Y", and if implementation diverged from the plan (it always does), the agent has two sources in conflict and no criterion for preferring one. The status field supplies the criterion at zero cost, independently of when the file physically moves.
- **The archiving script owns the archived-plan inventory.** Once a plan is excluded from the knowledge graph, the graph can no longer be queried to find plans that were archived but never status-marked, or status-marked but never archived. That reconciliation is therefore a responsibility of the archiving script, which maintains its own record of what it moved and when — it is not a knowledge-graph query and must not be specified as one.
- **The same reasoning extends to excluded documents, and the exclusion script owns that inventory.** Phase-one exclusion is only meaningful if phase two — delete later if nothing missed it — can find the set awaiting the decision, and an excluded document is by construction invisible to the graph that would otherwise list it. The exclusion script therefore maintains its own record of what it excluded, **when — with a timestamp and a sha**, and which inbound references were severed. Without it, "delete later" is a decision nobody can enumerate the subjects of, the severed-reference set needed for recovery is lost, and the retrieval-composition measurement below cannot be read against the intervention that changed it.
- **The inventory is updated by the severance step regardless of who performs it.** In the first shipment the severance is human-executed while the exclusion configuration is scripted, so an inventory written only by the script would be missing the severed-reference set during exactly the phase in which the design says a human does the severing — losing the recovery data at the moment it is most likely to be needed. Specify the inventory as an artifact with a mandatory update step attached to the severance itself, not as a side effect of the script.
- If, at the end of a feature, the plan contains information that would be painful to lose, that information belonged in the spec or in an ADR and never made it there. It is a signal about a missed transfer, not a reason to keep the plan alive. The correct response is to move the content to its proper artifact, then let the plan die on schedule.

#### On markers

- **Default is implicit:** unmarked content is current. Annotating a paragraph as "still true" is noise that ages worse than the content itself — a six-month-old `verified: true` is a false claim wearing a guarantee.
- **No meta-annotation inside code comments, ever.** A comment describing the verification status of another comment is the bottom of the barrel.
- The only persistent marker worth defending is per-document, not per-paragraph: `last-verified-at: <commit-sha>` in the front matter. It costs nothing, ages informatively rather than deceptively, and gives the agent a signal about how much to trust the file. It applies to documents whose format carries front matter; **a document whose format cannot carry it is treated like a source file — no marker, and no marker invented for it.**
- **The sha recorded in `last-verified-at` is the commit the document was verified *against*** — the repository state the agent read while classifying, i.e. the `HEAD` in effect at the start of the classification pass — **not the consolidation commit that writes the field.** Recording the consolidation commit would be circular: its sha does not exist until after the file has been written.
- **The recorded sha must remain resolvable in the integration branch after merge.** A sha the reader cannot resolve is not a weaker distance measure, it is the same class of lie as a stale `verified: true` — and in the merge-time case the baseline is a feature-branch commit, which a squash or rebase merge destroys. The field is therefore only admissible where the toolchain and merge strategy guarantee resolvability, or where a mechanical post-merge step maps the recorded sha to a surviving one. Which of those applies is toolchain-specific and left open below; what is settled is that a dangling sha is not an acceptable outcome and that the field is omitted rather than written unresolvable.
- **`last-verified-at` is written by exactly one pass kind under exactly one scope condition: a `document` pass whose declared scope is the whole document.** Three exclusions follow, and all three must be stated, because the earlier framing named only the first and left the other two open to a pass that would write the field on evidence it never gathered:
  - a **subset** document pass does not write it, because writing it would assert verification of content the pass never examined;
  - a **comment** pass never writes it, because a source file has no carrier and none is to be invented;
  - a **severance** pass never writes it, because its declared scope is reference occurrences and not document content — it edits a spec without having verified a single statement in it.
  The corollary is that a document consolidated across several review units carries no verification marker until the last of them completes, and that the tracking of the outstanding remainder is an open question below — deliberately not solved by inventing a partial-verification marker.
- **Isolation by commit is mandatory whenever the pass realigns a document to a functional change; stashing is admissible only for a standalone pass.** If the functional work is stashed rather than committed, the captured `HEAD` predates the change the document is being realigned to, so the agent verifies the document against code that does not yet contain the behavior in question — the exact failure the fixed ordering exists to prevent. It is also what the gate's ancestry check requires, since a stashed change leaves no commit for the baseline to be the parent of. Commit the functional work first in the merge-time case. Reserve stashing for a brainstorming-time consolidation that happens to have unrelated work in flight, where the captured `HEAD` and the tree the agent reads coincide.

#### On retrieval exclusion and deletion

- **Retrieval exclusion is the primary lever; deletion is the secondary one.** The same mechanism that makes archived plans invisible to retrieval works on any low-value document, at far lower risk and with no unrecoverable step. Deletion is therefore a **two-phase operation**: exclude from retrieval first, delete later if nothing missed it.
- **Exclusion is only as strong as its weakest channel, and unrestricted full-text search is a channel, not a residual.** Phase one is **exclude *and* sever inbound references**, and the channel list is: retrieval index, glob patterns, knowledge graph, inbound links from documents that remain in play, and the scope of any search tool the agent routinely uses. The correct statement: reachability by a *deliberate* human search of the tree is accepted residual and is not a reason to prefer deletion; reachability by the agent's routine search tool is a channel that must be closed, and where the toolchain cannot scope that tool, the exclusion cost claim is conditional and must be stated as such.
- **Exclusion is recoverable, but not costlessly.** Restoring an excluded file is a configuration change; restoring the inbound references that were severed is a revert against documents that have themselves been edited since, so the recovery cost rises with elapsed time and with the churn of the severed documents. State the property as *no unrecoverable step, with recovery cost rising after the fact* — not as *no irreversible step*.
- **Phase two has no trigger unless one is defined.** Two consequences are settled. First, the exclusion inventory is the only enumeration of the candidate set, so phase two is a review of that inventory and nothing else. Second, in the absence of a defined miss signal, the correct default is **exclusion is permanent and phase two never runs**, which costs a retained file nobody retrieves and forfeits almost nothing, since the benefit was captured in phase one. What constitutes evidence that nothing missed an excluded document is open below; that the design does not depend on the answer is settled.
- **Severing inbound references is a destructive edit on documents that stay in play, and is governed as one.** It removes lines from surviving specs and docs, so it is a separate commit, it counts against the bounds of its review unit, and it is reviewed by reading the `-` lines like any other consolidation — **by someone other than its author**, with deferral rather than self-review where no second reviewer is available. Whether an agent may *perform* the severing autonomously at all remains open below, and the first shipment is scoped accordingly.
- **A severance pass carries a classification record like any other consolidation pass, and its floor is the exclusion inventory.** The record's shape for this pass kind is fixed: **pass kind `severance`; unit rule "one inbound reference occurrence", declared by name from the closed enumeration; declared scope the set of surviving documents holding references to the excluded target; one entry per occurrence, disposed `severed` or `retained`.** The non-agent-authored floor under its declared scope is the exclusion inventory's enumeration of inbound references, not the knowledge graph — which cannot see the excluded target — and the header's floor-provenance field records the inventory's observation state accordingly.
- **A severance pass is a pass kind of the document-consolidation skill, not a third skill.** It operates on documents, produces a record, obeys the same procedure, and needs arbitration only where a reference turns out to be load-bearing. Assigning it to that skill is what keeps "exactly two skills" true while giving the severance pass an owner; leaving it inside the exclusion script would make it the silent side effect the design explicitly forbids it from being.
- **The exclusion machinery has a second, non-destructive use.** It is the mechanism that lets a record be kept in the repository without being kept in the context: committed, versioned, reachable by a human who goes looking, invisible to retrieval. Present exclusion as a general lever for separating *retained* from *retrievable*, not solely as a disposal step.
- **A newly committed record is created outside retrieval; it has no inbound references to sever.** Where the classification record is materialized as a committed file, the exclusion step is *configuration only*. The pointer in the commit message is not an inbound reference in the relevant sense, because commit messages are outside retrieval by construction.

### Rules vs. skills — the split to encode

These are not alternatives. **Rules prevent accumulation; skills repair what accumulated anyway.** Rules alone leave the pre-existing debt untouched (they do not apply retroactively); skills alone condemn the project to perpetual maintenance.

The assignment criterion is mechanical: a directive belongs in a **rule** if it must apply *always, at zero activation cost*; it belongs in a **skill** if it is a *rare, multi-phase procedure with risk of information loss*; it belongs in a **script or hook** if a shell command could do it.

**Rules** (`CLAUDE.md`, deliberately kept under ~20 lines for this domain — a 300-line `CLAUDE.md` is no longer a rule set, it is documentation the agent dilutes):

- the artifact taxonomy;
- the no-append rule on specs, **stated with its justification** ("history lives in git and in ADRs");
- the comment policy: only what the code cannot say about itself; no bug-fix references, **stated with its justification**;
- the implicit default: unmarked = current;
- the obligation to **flag rather than rewrite** anything that is no longer verifiable;
- **the location of the escalation intake.**

**The intake's location is a rule line, not an implementation detail, and it makes the intake's path a prerequisite of the first shipment rather than a parallel decision.** The flag-rather-than-rewrite obligation is inert if the agent has to guess where the flag goes, and a rule that resolves to a guess resolves differently every session. State the ordering dependency explicitly: the intake's path, format, and churn-stable reference scheme must be **decided before the rules ship**, not alongside them.

**How the taxonomy fits the line budget, shown rather than asserted.** In `CLAUDE.md` the taxonomy is **one line per artifact, function plus a lifecycle keyword only** (state / ephemeral / append-only / state), with a pointer to the project overview for the lifecycle detail. The full table lives in the overview and is not duplicated in the rule set. The deliverables must show the arithmetic, not claim it:

| Rule-set line | Lines |
|---|---|
| Taxonomy, one line per artifact | 4 |
| No-append rule on specs | 1 |
| — its justification | 1 |
| Comment policy | 1 |
| — its justification | 1 |
| Unmarked = current | 1 |
| Flag rather than rewrite | 1 |
| Escalation intake location | 1 |
| Pointer to the overview for lifecycle detail | 1 |
| **Total** | **13** |

Treat the line budget as binding and the taxonomy rule as a compressed index, not as an explanation. The remaining headroom is deliberate slack, not an invitation.

**Scope of the justification requirement.** Justifications are attached to the **two rules the agent will otherwise rationalize its way around** — the no-append rule and the comment policy — because both ask the agent to destroy information. The remainder are declarative and self-enforcing. Do not treat "rules carry their justification" as a universal that conflicts with the line budget; treat it as targeted.

**The flag-rather-than-rewrite rule requires an intake, and the intake ships with the rules.** The intake is a **convention plus a location** — a single append-only destination for suspected defects, unverifiable statements, and observed obsolete-citation events, with the minimum fields needed to act on an entry:

- what was observed;
- where — the unit reference, **in a form stable under file churn**;
- the originating context — the pass that produced it, or the session in which it was noticed;
- **the sha in effect when the observation was made**, which exists for all three entry kinds and is therefore required rather than conditional;
- the entry's state — `open`, `resolved-actioned`, or `resolved-confirmed-external`;
- **for a resolved state, the ruling sha** — the sha at which the ruling was made, distinct from the observation sha. Required for the same reason `last-verified-at` records a sha rather than a boolean: a terminal `resolved-confirmed-external` is a durable statement that a person once ruled a unit acceptable, and without a repository state attached it becomes precisely the stale `verified: true` this design refuses, relocated out of the file where it is harder to notice. The ruling sha is also what a later `resolved-already-actioned` disposition cites;
- the entry kind, which the consumer may **reclassify in place** rather than by appending a new entry;
- **for the obsolete-citation kind only, an observation count and the sha of the most recent observation.**

Three properties of the intake script are settled and each closes a defect in the earlier specification:

- **The dedup key is the churn-stable unit reference alone, not the pair of reference and kind.** Keying on the pair breaks against the reclassification rule: if a consumer reclassifies an entry from unverifiable to suspected defect, a later pass observing the same unit under the original kind finds no suppressing entry and appends a duplicate. The append is therefore suppressed where **any** non-suppressed entry exists for that reference, and the script surfaces the existing entry so the pass can request reclassification instead of appending.
- **The obsolete-citation kind is exempt from suppression and is counted instead.** Suppressing the second observation of the same stale statement destroys the frequency signal that the observation window explicitly exists to measure — *how often the obsolete-citation trigger fires at all*. The resolution: the entry is not duplicated, and each further observation increments its count and updates its latest-observation sha. This keeps the no-duplicates discipline and the measurement simultaneously; the earlier blanket idempotence rule sacrificed the measurement without noticing.
- **The admissible states differ by kind, and leaving that unstated leaves a consumer guessing.** `resolved-confirmed-external` is meaningful only for the unverifiable-statement kind, where a person has ruled a statement true but unconfirmable in the repository. A suspected defect resolves to `resolved-actioned` — the defect was fixed, or the documentation was corrected on human authority. An obsolete-citation event resolves to `resolved-actioned` when a consolidation pass consumes it. State the mapping.

It is not a skill and not a rule; it is a file convention and, at most, a script that appends to it. **The intake's shape is settled; only its path, its format, and its churn-stable reference scheme are open** — and those three are prerequisites of the first shipment, per the ordering dependency above.

**Skills — exactly two.** The division criterion is *not* the artifact type, and it is *not* that one skill deals in local truth while the other deals in external truth — both encounter external truth. It is **what external truth does to the pass**:

1. **Comment consolidation.** What the agent verifies autonomously is **redundancy and obsolescence, against the code, inside the repository**. But the category the skill exists to *preserve* — an external constraint, an invariant not expressible in the type system — is by definition not verifiable in the repository, so this skill meets tier-3 content routinely rather than exceptionally. For this skill, external truth is a **stop condition**: the unit is frozen byte-for-byte, escalated through the intake, and the pass moves on. It never becomes work the pass has to finish. That is what makes the skill largely autonomous — not a local truth source. It may **not** decide autonomously when comment and code disagree; that escalates. Pass kind: `comment`.
2. **Spec and design-doc consolidation.** Truth source: the code **plus** business rules that live outside the repository, and here external truth is **work to be arbitrated**, not a stop condition. The agent produces the exhaustive classification, rewrites what is verifiable, and hands over a `## To be confirmed` section that a person must rule on before the pass completes. Pass kinds: `document` and `severance`.

**"High-volume" is the wrong word for the comment skill.** Autonomy per pass is not throughput in aggregate. Both skills are bounded by the same single review budget, so neither produces more reviewed consolidation per week than the reviewer absorbs; what differs is that the comment pass does not *block* on arbitration while the spec pass does. Combined with the conservative reconstructor standard, whole-unit freezing, and the removal cap, the comment skill's aggregate return is a measurement question, not a property to assert. State it as: *high autonomy per pass, non-blocking, aggregate return to be measured.*

**Higher automation is not lower risk.** Comment consolidation is the more autonomous skill because external truth stops it rather than blocking it, not because its errors are cheaper. Its characteristic failure — a deleted invariant — is the single most expensive outcome in this whole design, and it is invisible in the resulting document by construction.

**Each skill states its bound, and the bounds are not the same kind of thing.** For comment consolidation the binding constraint is numeric and mechanical: the two-part bound per review unit, enforced at a gate that sees the whole unit. For spec consolidation the binding constraint is the mandatory human arbitration step, with the two-part bound applying on top as a review-capacity ceiling. Require each skill definition to name its bound explicitly and to say which kind it is. **State also that a skill shipped before the review-capacity calibration exercise has a placeholder where its numeric bound should be, and a placeholder cap is not a bound** — which makes that exercise a blocking prerequisite of shipping either skill rather than a parallel activity.

Merging these two into one skill costs twice: irrelevant instructions get loaded, and — worse — the trigger description becomes generic, so the skill fires when it shouldn't and fails to fire when it should. Trigger precision is the real design constraint of skills. Fragmenting into five has the opposite problem: overlapping triggers, arbitrary selection, and loss of the ability to reason about what was actually done.

**Shared machinery, not duplicated prose.** Both skills face the same scoping problem, and the strategy for solving it must live in **one place both skills invoke** — a target-set selection script over the knowledge graph — not as two prose scoping sections inside two skill definitions. The skills differ in what they do with the target set, not in how they choose it.

**Neither rule nor skill** — mechanical operations that must not consume a context load to perform what `sed` would do:

- marking a plan `completed`, and rewriting an ADR's `status` on supersession → a merge-checklist step or a hook; both exempt from the isolation rule;
- archiving plans, excluding them from retrieval, and maintaining the inventory that reconciles status marking with physical archiving → a script plus retrieval configuration;
- excluding low-value documents from retrieval (phase one of deletion), and maintaining the timestamped inventory of what was excluded, when, and which inbound references were severed → the same script and configuration, with the inventory's severance fields updated by whoever performs the severance;
- target-set selection for both consolidation skills → a single shared script over the knowledge graph, invoked by both, **recording the floor's provenance and observation state alongside its output**, with that output either committed in the review unit or re-runnable by the gate;
- **coverage verification of the classification pass** → a script that counts the classifiable units **within the pass's declared scope, as they exist at the verification baseline sha**, according to the declared unit rule drawn from the closed enumeration, and compares that count against the number of classification entries. Counting against the working tree at commit time would be incoherent: consolidation removes classifiable units. **It runs twice: locally, before the rewrite, as a gate on proceeding; and at the review-unit gate, against the materialized record, recomputing the unit count itself rather than reading a count the record asserts.**
- **removal-authorization coverage** → a script that maps every removed line in every consolidation-class commit of the unit onto a classification entry and fails where the line has no entry or the entry's disposition does not authorize removal;
- **cross-checking the declared scope, the baseline, and the floor's freshness** → the same script compares the declared scope against the output of the shared target-set selection script and fails in **both** directions — broader than the target set, or narrower without one of the two enumerated reasons (bound-driven split, freshness exclusion). It also fails where the recorded floor observation state is stale relative to the verification baseline beyond the threshold, and where the declared baseline is not the parent of the first content-removing consolidation commit in the unit;
- **enforcement of the two-part bound** across a consolidation review unit → a check at a gate that observes the whole unit, accumulating removed lines and removal judgements over every consolidation-class commit in it; the judgement half additionally checked pre-rewrite locally, the line half additionally projected pre-rewrite as an upper bound, **both halves re-checked at the unit gate against the materialized record**;
- appending an entry to the escalation intake → a script, invoked by either skill, idempotent on the **churn-stable unit reference**, supporting reclassification in place and occurrence counting for the obsolete-citation kind, never a hand-written note in chat;
- updating `last-verified-at` → a side effect of a skill, not a skill, and only on a whole-document `document` pass whose recorded sha is resolvable post-merge;
- **capturing the baseline measurement the observation window depends on** → a script plus, where the retrieval channels are not introspectable, a defined manual sampling procedure, shipped with the rules and **executed before the first exclusion is applied**.

**The coverage check needs a machine-readable input, and the classification record is that input.** The classification is written, during the pass, to a **structured record at a conventional path in a fixed line-oriented or key-value format**, one entry per classifiable unit. That record is the coverage script's input, the source from which the gate-readable form is materialized, and the thing the human reads alongside the diff. Do not specify a format the toolchain has not been observed to support; mark the format choice and path as open. What must not happen is a coverage check specified against an input that does not exist.

**The record's header declares the six things every check reads.**

| Header field | The check that would be undefined without it |
|---|---|
| Pass kind (`document` \| `comment` \| `severance`) | Which floor applies, which disposition set applies, and which cap values apply if they differ by pass type. |
| Review-unit identity | The bound cannot accumulate across a unit it cannot delimit. |
| Unit rule, named from the closed enumeration | The coverage count cannot count units without an evaluable rule. |
| Declared scope, with a narrowing reason where narrower than the target set | Coverage would fail by construction on every split pass; and narrowing could not be distinguished from evasion. |
| Verification baseline sha | The count would be taken against the wrong tree; and the ancestry check has nothing to floor. |
| Floor provenance and its observation state | The scope cross-check cannot know whether its own floor is sound. Instantiated as the graph's build state for `document` and `comment`, the exclusion inventory's state for `severance`. |

**Required contents of a classification entry.** Each entry carries: the churn-stable unit reference, the disposition, and the evidence its disposition requires per the disposition table — a specific code location or identifier for any disposition asserting a fact about the code, a regenerability basis stated against the reconstructor standard for `regenerable → delete`, the intake entry and ruling sha for `resolved-already-actioned`, the exclusion-inventory entry for `severed`, a reason for `retained`. A bare disposition is producible without reading anything; a citation is not.

**The record is materialized in the review unit; the working-tree copy is transient.** Three decision rules are settled. First, **the working-tree copy must not be swept into the consolidation commit** unless the committed-file channel was chosen deliberately. Second, where the committed channel *is* chosen, the record goes in **its own commit** within the review unit, never first, contributing zero to both caps. Third, **where the toolchain cannot reliably keep a transient file out of a commit, choose the committed-and-excluded channel outright**. Uncommitted scratch output is not a third channel; it satisfies no gate.

### The consolidation procedure

1. **Isolate the working tree.** Consolidation is always a separate commit, never mixed with functional changes. In the merge-time case this means a separate commit within the same pull request; in the brainstorming-time case a standalone commit with no host PR. Bring the working tree to a clean state first — in the merge-time case by **committing** the functional work, never by stashing it, for the reasons given in step 3; in the standalone case by committing or stashing whatever unrelated work is in flight. A pass that would exceed either part of the review unit's bound is split into separate review units, not into more commits inside the same one, and not across concurrent sub-agents. Where the host pull request's own functional diff is large, the realignment moves out and becomes a standalone pass; where it rides along, the admissible consolidation *line* volume is the residual after the functional diff.
2. **Scope before classifying, and declare the scope.** Run the shared target-set selection script. Blanket scope is the failure mode, not the safe default. Record the declared scope in the record header, with a narrowing reason where it is narrower than the target set, together with the pass kind, the review-unit identity, the unit rule named from the closed enumeration, and the floor provenance and observation state; commit the target-set output inside the review unit, or ensure the gate can re-run it. Where a single file alone would exceed the bound, the declared scope is an explicitly enumerated subset of that file and the pass does not write `last-verified-at`.
3. **Record the verification baseline.** Capture the sha the pass is being verified against — `HEAD` after step 1's isolation and before any file is read — into the record header. Capturing it before the functional work is committed would record a state the agent never examined, which is also why the functional work must be committed rather than stashed; capturing it after classification would record a state that includes the pass's own writes.
4. **Classify. Do not rewrite yet.** Pass 1 assigns every classifiable unit **in the declared scope** — per the declared unit rule — exactly one disposition from the set applicable to the pass kind, applying the precedence order where more than one fits. Write each disposition, with its churn-stable unit reference and its required evidence, into the structured record as the pass proceeds.
5. **Verify coverage, scope, baseline, and the judgement half of the bound — all before rewriting anything.** Run the checks against the record: classifiable units in the declared scope at the baseline in, entries out, counts must match; the declared scope cross-checked in both directions with its narrowing reason; the floor's observation state checked for staleness; the baseline checked as parent of the first content-removing consolidation commit; the removal-authorizing entry count checked against the judgement cap; and the **projected** removed-line upper bound — the summed lines of all removal-authorizing units at the baseline — surfaced to the author as a re-scope decision where it exceeds the line cap. Be precise about what this buys: the count check defeats **omission within the declared scope** and nothing else. The cross-check raises the floor under scope plausibility but does not establish that the declared scope was *right*. Neither defeats **skimming**, because an agent that skims the middle of a long document can still emit one plausible disposition per unit and pass the count perfectly. Skimming is addressed by the citation requirement in step 4 plus a **human spot-check of a sample of entries against the file**, performed as part of the human review of the review unit and gating its merge. A count-only check reported as coverage evidence is worse than no evidence, because it gets trusted.
6. **Rewrite.** Only now. Without the forcing pass in step 4 and the gates in step 5, the agent jumps straight to synthesis, and that is where loss occurs.
7. **Measure the line half of the bound, and treat failure as re-scoping rather than as a finding to reconcile.** The measured removed-line count exists only after the rewrite; the projection in step 5 is an upper bound, not a substitute. Admissible remedies are enumerated in advance: split the pass across review units and re-run, or discard and re-scope. Raising the cap, redistributing across more commits inside the same review unit, and fanning out across agents are not remedies.
8. **Materialize the record inside the review unit, and keep it out of the persisted document and out of the consolidation commit.** The record is materialized through one of the two channels named above. Either way it is attached to the exact diff it describes, outside retrieval, and still available in six months when someone asks what the pass actually looked at. The sole content that crosses from the classification into the document is the `not verifiable` bucket, as the `## To be confirmed` section in step 11 — items, not the record, and only that bucket. Rationale for exhaustiveness: if the agent flags only what it believes obsolete, silence becomes ambiguous between "verified, current" and "never examined" — two radically different things the human cannot distinguish. And "never examined" is the common case, because attention over a long document is not uniform. The verdict per unit matters less than the guarantee that every unit in scope was looked at.
9. **Verify against the code, not against the document.** Nothing survives unless it is verifiable in the current code or is a genuine decision, constraint, or rationale.
10. **`contradicts code → suspected defect` is never resolved by the agent.** The statement is left in place, unmodified, at the granularity of the whole declared unit, and the divergence is reported into the escalation intake — not only into the transcript, and not a second time if a suppressing entry already exists for that reference.
11. **`not verifiable` is the critical bucket.** It is never deleted silently. In a document pass it goes into a `## To be confirmed` section *and* into the intake; a later pass disposes each item as `not verifiable` if still open, or `resolved-already-actioned` if the intake shows a ruling. In a comment pass there is no in-file carrier and none is created. In either case the freeze applies to the whole declared unit and the escalation is subject to read-before-append against a churn-stable reference.
12. **Review the removed lines, not the result.** Reading the final document does not reveal what was lost; reading the `-` lines does. Read them against the classification record. The removal-authorization check mechanizes the crudest form of this — a `-` line with no authorizing entry — but it cannot judge whether an authorized removal was correct, which is what the human is for. This step and the entry spot-check in step 5 together constitute the review budget of the unit, and they are the only real control on the regenerability test.

### Triggers

Correct:

- completion of a feature or epic (the plan dies; what it taught flows back into the spec);
- **at the start of brainstorming on an area touched in the past** — this grafts onto the existing workflow and yields clean context before the most token-expensive phase, and is the case where the consolidation commit stands alone rather than riding inside a feature PR;
- whenever the agent is observed citing obsolete information — the most reliable diagnostic signal.

Wrong: **mid-implementation. Never.**

**The obsolete-citation trigger is a signal, not an authorization.** It arrives mid-implementation more often than not, which is precisely where consolidation is prohibited. The resolution: the observation is **recorded into the escalation intake when it happens — incrementing the entry's occurrence count where one already exists — and consumed at the next admissible boundary**: feature completion, or the next entry into brainstorming on that area.

Calendar-based triggers are inferior to event-based ones. Doing it "by feel every once in a while" is the worst mode, because information loss happens precisely when no checklist is in play.

### The asymmetry that must be explicit

Encode **three tiers**:

| Tier | Truth source | Agent authority |
|---|---|---|
| **Code-verifiable** | The code, unambiguously | Decides autonomously. Redundant comments deleted, obsolete statements rewritten, stacked layers collapsed. |
| **Code-visible, intent-ambiguous** | The code shows a divergence, but not which side is correct | **Reports, does not resolve.** A comment/spec statement that contradicts the code is a suspected defect, not a stale document. |
| **External truth** | Business rules, regulation, contracts — outside the repository | **Escalates.** No autonomous deletion under any circumstance. |

The middle tier is the one that gets omitted and the one that causes the most expensive failures. Without the top tier's boundary made explicit, the outcome is technically impeccable consolidations that delete a regulatory constraint nobody had implemented yet. Without the middle tier, the outcome is documentation quietly rewritten to describe a bug as intended behavior.

Both lower tiers terminate in the same place: the escalation intake. A tier distinction that does not end in a durable destination is a taxonomy, not a control.

The outer tier is not the rare case. Both skills meet it routinely, and they differ only in what it does to the pass.

**Present the table with its limitation attached:** the tiers partition authority, they do not independently verify the judgement that assigns a unit to a tier.

### Critical positions to carry into the project — do not soften these

- **The optimization target is upstream, not downstream.** Reducing after the fact costs far more than not accumulating in the first place. If only one thing gets built, it is append-resistant documents by construction. The consolidation skills are maintenance, not the solution.
- **Many documents should not be compacted — they should be removed from play.** A significant share of documentation in an AI-assisted codebase is write-once, read-never. The question to ask of every file is "if this disappeared, what would break?" Aggressive removal returns more than accurate compaction, and costs less. Execute it as retrieval exclusion first and deletion second: the context-cost benefit is captured by exclusion **provided every channel is closed — inbound references and the agent's routine search scope included**.
- **The return on comment consolidation is bounded in a way the return on document exclusion is not.** Excluding a document removes it from retrieval entirely; comments are only ever read as part of a file the agent was going to read anyway, so consolidating them shortens files already in scope rather than removing anything from scope. The saving is real but second-order, while the characteristic failure — a deleted invariant — is first-order. Three further compressions of that return are settled above: the conservative reconstructor standard, whole-unit freezing, and the exclusion of prose from the regenerability test. Confirm the demand *and* the yield by measurement rather than assumption.
- **The enemy is not length, it is contradiction.** A long, coherent, true document costs tokens. A short one with three conflicting statements costs correctness. Optimize non-contradiction first, brevity second.
- **Both skills are, first and foremost, scoping problems.** The expensive part is not rewriting; it is deciding which files to work on. The target-set selection strategy must be defined before the procedure, must live in shared machinery, and the knowledge graph is the natural instrument — subject to the graph being a stated precondition, to its staleness invalidating rather than weakening the control, and to the target set reaching the gate by a path that is not the agent's narration.
- **Every control in this design must be mechanical or it is not a control.** Where a script can verify a claim, the script is mandatory and the claim is not accepted on its own. A control whose input does not exist — a coverage check with nothing to count, an escalation with nowhere to land, a gate check reading a record that was never materialized — is the same failure in a more flattering shape. So is a control whose parameters are supplied by the party being controlled, unless something not agent-authored puts a floor under them; so is a control whose non-agent-authored floor is stale; and so is a control that compares two numbers the controlled party produced.
- **Where a quantity is not mechanically recomputable, say so instead of implying it is.** The removal-judgement count is derived from agent-written dispositions and no script can independently verify a disposition was correct. Naming its floors — one-disposition-per-unit coverage, removal-authorization coverage, and the human spot-check — and naming the residual exposure is what keeps the recompute principle honest. A design that asserts universal recomputation has one unexamined self-report at its centre.
- **Mechanical is necessary and not sufficient: a check must also measure the property it is credited with.** Every control in the deliverables states what it verifies **and what it does not** — the count check catches omission within the declared scope and not skimming; the target-set cross-check raises the floor under scope plausibility without establishing the scope was right, and only where the floor is fresh and did not arrive by narration; the baseline ancestry check floors which tree was counted and says nothing about whether it was read; the removal-authorization check catches unrecorded and mislabelled removals and says nothing about whether an authorized removal was correct; the removed-line cap bounds reading volume and the removal-judgement cap bounds judgement volume, neither saying anything about correctness; `last-verified-at` measures distance from the verified state and not the quality of the verification, is absent rather than approximate after a subset pass, absent for comment and severance passes entirely, and absent rather than dangling where the sha would not survive merge; the tier table partitions authority and does not validate tier assignment.
- **Check ordering is part of a control's specification, and the one unavoidable exception is stated rather than hidden.** Every check is placed before the step it authorizes, with exactly one exception — the *measured* removed-line count, which cannot exist before the rewrite, and whose pre-rewrite projection reduces but does not eliminate the exception — and that exception ships with enumerated remedies precisely so that the pressure to reconcile the work to the check has a pre-agreed answer.
- **Human review capacity is a single budget with several claims on it.** The removed-line cap, the removal-judgement cap, the `-` line reading, the entry spot-check, and — in the merge-time case — the functional diff sharing the sitting are five demands on the attention of one reviewer in one pass. Any proposal that tightens one by loosening another has not improved the design. The unit rule's granularity is a claim on the same budget, and so is the number of review units produced per week — which is why concurrency across review units is barred. **The severance reviewer's non-authorship is a claim on a second person's budget**, which is why the two-reviewer precondition is stated as a precondition.
- **The observation window must be instrumented before it opens, and the instrumentation must not be confounded by the intervention it is meant to prioritize.** Four requirements, all settled:
  - **Unconditional capture:** intake entry counts by kind and by state, plus obsolete-citation occurrence counts. Implementable the day the rules ship.
  - **Conditional capture:** the composition of retrieved context per session by artifact type, dependent on the retrieval channels being introspectable. Where they are not, a **defined manual sampling procedure** is the fallback and the comment-versus-exclusion priority is calibrated from a sample rather than a census — not silently dropped while the claim is kept.
  - **Capture precedes intervention.** Exclusion ships in the first shipment, so applying it during the window changes retrieval composition as the window runs. The baseline must therefore be captured **before the first document is excluded**, and every exclusion must be timestamped in the inventory so the composition series can be read against the intervention. Shipping the machinery is not the same as running it. Without this, the window measures the intervention and calls the result a baseline.
  - **Define the window in events, not weeks.** The design's own triggers are event-based, and a two-week window may contain no admissible trigger at all, in which case it produces nothing about either skill. The window is therefore a number of admissible trigger events — feature completions and brainstorming entries on previously-touched areas — with calendar time as a floor rather than the definition. How many events is open below; that a window containing no trigger is not a window is not.
  - **None of it calibrates the review budget.** Intake counts and retrieval composition say nothing about how many removed lines a reviewer reads before quality falls off. The review-budget numbers require their own exercise: a small number of deliberately measured review passes over consolidation-shaped diffs, recording volume, time, and defects caught. That exercise is a **blocking prerequisite of shipping either skill**, and the observation window does not produce it.
- **Recommended sequencing:** ship the rules first, together with the escalation intake they depend on, **the retrieval-exclusion and plan-archiving machinery**, and **the baseline measurement capture**, and build neither skill for the duration of the observation window. Three ordering dependencies are load-bearing:
  - the intake's path, format, and reference scheme are decided **before** the rules ship, because a rule line pointing at an undecided path is a rule that resolves to a guess;
  - the baseline capture runs **before** the first exclusion is applied;
  - phase-one exclusion requires severing inbound references, and whether that is safely agent-executable is open below, so in the first shipment **the severance is performed by a human, reviewed by a different human, and carries its own classification record**. The exclusion benefit therefore accrues at human throughput until that question closes, which qualifies the return-per-unit-risk claim without overturning it and makes closing that question the highest-value item on the open list. Where no second reviewer exists, the severance half does not ship at all.

  The exclusion benefit is additionally conditional on the agent's routine search scope being constrainable; where it is not, the first shipment's headline claim is weaker than stated and the deliverables say so. Rules are the highest value-to-cost intervention and they are *diagnostic*. Expected outcome (a prediction, worth less than the observation): rules absorb most of the problem on new documents, exclusion absorbs much of the remaining context cost, and the skill actually needed is the comment one, where pre-existing debt is largest and rules do not reach retroactively. **Read this as a prediction about demand, not about safety and not about yield.**
- **Specified is not scheduled.** Both skills are fully specified in the project knowledge document; only the rules, the intake, the mechanical machinery, and the measurement capture are scheduled first. Specifying both is cheap and sharpens the rules by forcing the boundaries to be drawn. Do not read the sequencing advice as a reason to leave a skill under-specified.
