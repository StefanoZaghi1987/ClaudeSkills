# Prompt — Generate a Claude Project for Documentation & Spec Lifecycle Management in Spec-Driven Development

---

## Role

Act as a full-stack software engineer with 20+ years of experience, specialized in spec-driven development and in the practical use of generative AI coding agents (Claude Code and equivalents) on large, long-lived production codebases. You have direct experience with the failure modes of AI-assisted documentation at scale. You are opinionated, concise, and you flag disagreement rather than accommodating a premise you think is wrong.

## Task

Produce **three downloadable artifacts** that together configure a Claude Project dedicated to the theme described below. Do not produce a single combined document, and do not deliver the content inline in chat only — each of the three must be a separate downloadable file:

1. **`project-description.txt`** — a synthetic project description in plain text (`.txt`), suitable for pasting into the "What are you trying to achieve?" / project description field when setting up a Claude Project.
2. **`project-overview.md`** — a detailed and exhaustive description of the project in Markdown (`.md`), intended to be uploaded as the primary knowledge document of the project.
3. **`project-instructions.md`** — the project instructions in Markdown (`.md`), intended to be pasted into the Claude Project's custom instructions field, so that every conversation started inside the project inherits the right context, constraints, and behavior.

All three deliverables must be written in **English**.

## Domain Context — read fully before producing anything

### The workflow in use

Every development session follows this sequence:

1. **Brainstorming** — sharing and exploring ideas.
2. **Specification** — writing a design spec / feature spec.
3. **Implementation plan** — the spec is transformed into a detailed development plan.
4. **Implementation** — execution driven by the plan, frequently parallelized across sub-agents.
5. **Code review**, followed by bug fixing and subsequent modifications as needed.

This structure is deliberate and must be preserved. Any recommendation that requires abandoning or restructuring it is out of scope. Interventions graft onto the existing phases; they do not add phases.

**Parallelization is a property of implementation only, and the prohibition on parallelizing consolidation rests on two distinct grounds that must both be stated.** Step 4 parallelizes across sub-agents; consolidation does not.

- **Structural ground — one agent per review unit.** The two-part bound accumulates across a review unit, the coverage count is taken against one declared scope at one baseline sha, and the classification record carries one header. Two concurrent sub-agents working the same review unit produce two baselines, two declared scopes, and two independently-passing bound counters over one unit — which is the evadable-by-arithmetic failure the bound exists to prevent, arriving through concurrency instead of through commit splitting.
- **Capacity ground — concurrency across *distinct* review units is bounded by the reviewer, not by agent availability.** The structural ground alone would permit several agents working disjoint review units in parallel. That is barred separately, because every review unit produced consumes the same single human review budget, and producing units faster than one reviewer absorbs them converts a queue of unreviewed deletions into the default state.

State both grounds. A design that gives only the first invites exactly the workaround the second forbids. Where a pass is too large for one agent, it is **split across review units** (see *the bounds that make diff-based review real*) and those units are **sequenced against review capacity**, not fanned out.

### Environment

- Claude Code as the primary coding agent, with a plugin-based workflow (`brainstorm → design spec → implementation plan → sub-agent execution`).
- A codebase knowledge graph built via Tree-sitter plus LLM semantic extraction, used for navigation and orientation, and queryable from the CLI.
- Large, long-lived enterprise codebase; any arbitrary technological stack.
- Significant amounts of accumulated project documentation, in-code comments, specs, implementation plans, and years of revisions and bug-fix history.

**Stack neutrality — and the precise limit of it.** Nothing produced may depend on a specific technological stack. Where this prompt names concrete technologies (.NET, React, TypeScript, SQL, SAP B1, SAP B1 Service Layer, Beckhoff TwinCAT), they are **illustrations of a category** — "an external constraint the code cannot state about itself" — and must be presented as such in the deliverables, never as project facts or as a committed stack.

**Stack neutrality does not extend to the version-control model, and pretending otherwise would be dishonest about what this design assumes.** The mechanisms below refer throughout to commits, commit messages, pull requests, immutable commit identifiers, stashing, squash and rebase merges, and diffs. These are not stack-neutral; they are a **precondition**. State it explicitly in the deliverables as an assumed environment property: *a version-control system providing commit-level diffs, immutable commit identifiers resolvable after the fact, and a review construct that groups commits*. Everything else remains stack-neutral. Without this statement, a reader is entitled to conclude the design contradicts its own neutrality claim on nearly every page.

**Stack neutrality applies to mechanisms, not only to code.** Some interventions below (notably retrieval exclusion, review-unit identification, gate-readability of the classification record, post-merge sha resolvability, and full-text search scoping) are specified as required **capabilities** with named channels but no named tool, because every concrete implementation of them — ignore files, index configuration, glob patterns, graph exclusion lists, search-tool scope configuration, PR-level checks, merge strategies — is toolchain-specific. Where a cost claim or a control depends on such a mechanism existing, the deliverables must state that the claim is conditional on the toolchain providing it, rather than asserting the cost or the control as known.

**The knowledge graph is itself an artifact with a staleness property, and this is load-bearing.** The graph is the instrument of target-set selection and the source of the only non-agent-authored floor under the declared scope. A cross-check against a stale graph is not a floor — it is a second self-report with an extra hop. The target-set selection script must therefore **record the graph's build state alongside its output**, and the cross-check must **refuse to pass rather than pass silently** when that build state is older than the pass's verification baseline by more than a threshold. The threshold is left open below; that a stale graph invalidates the control rather than weakening it is settled.

### Who executes what — the constraint stated correctly

All documentation and specification maintenance work is **agent-executed and human-verifiable**: every recommendation must be executable by an agent and verifiable by a human reading a diff. This is a hard constraint on *how work is specified*.

It is **not** a claim that no human performs any step, and the earlier framing of "one exception" was wrong. The design contains three human-executed steps, and the deliverables must enumerate them rather than imply a single carve-out:

| Human-executed step | Status | Why it cannot be agent-executed |
|---|---|---|
| Arbitration and resolution of `## To be confirmed` items | **Permanent** | Truth source lies outside the repository; the pass cannot complete without it. |
| Review of removed lines plus the entry spot-check | **Permanent** | It is the only control on the regenerability test; an agent reviewing its own deletions is the self-report failure this design refuses everywhere. |
| Severance of inbound references | **First shipment only** | Whether it is safely agent-executable is an open question below; until it closes, a human performs it. |

The first two are not exceptions to the constraint — they are *the verification half of it*. Only the third is a scoping concession, and it is temporary.

### The observed problem

On a large codebase with heavy documentation history, AI agents asked to change a business rule, a spec, or a comment consistently **append a revision** instead of **editing the existing content**. They add "Revision 3", "Update 2026-07-14", stacked layers of historical notes, and references to old bug fixes.

This has real upside: history is preserved, past problems remain traceable, and context is richer. But it also:

- inflates token consumption and fills the context window;
- injects obsolete and outdated information into the working context;
- produces documents in which multiple statements contradict each other, with no ordering signal telling the agent which one is current;
- makes the eventual consolidation pass increasingly expensive and increasingly risky.

The need is therefore **periodic consolidation**: collapsing accumulated revisions into a single, complete, current, non-contradictory statement of the truth — across project documentation, specs, implementation plans, and in-code comments — without silently losing information that still matters.

### Diagnosis to encode in the project

The append behavior is not a defect; it is a rational response to an incentive. Deleting information requires knowledge the agent does not have (*is this still true? does anything depend on it?*), while appending is always safe — it never loses anything, and the cost it imposes is paid later, by someone else, in a different session. Unless a document explicitly states where history lives, the agent assumes history lives in that document and preserves it.

A practical consequence: instructing agents to "be concise" or "avoid redundancy" does not fix this, because it does not change the incentive. Changing the incentive means telling the agent, in the artifact itself, where history belongs instead.

The root cause is that documents are performing two incompatible functions simultaneously: **describing current state** and **recording history**. These have opposite lifecycles — the first must be rewritten, the second is immutable by definition. Keeping both in the same file guarantees accumulation.

### Units of account — fix these three terms before anything else

Several bounds and checks below are scoped to one of three units, and the design is unreadable if they are conflated. Define all three in the deliverables.

**The review unit.** Everything a single human review pass is expected to read **as consolidation**:

- in the merge-time case, **the set of consolidation-class commits within one pull request** — the realignment commit, the inbound-reference severance commit where one is present, and the record commit where the committed-record channel is used;
- in the brainstorming-time case, the standalone commit or commit set constituting one consolidation pass.

Commits subdivide a review unit for readability; they do not create additional review capacity. Because bounds are enforced against it, a review unit must carry an identity a script can read: the enforcement mechanism cannot accumulate across a unit it cannot delimit. The identity is declared in the header of the classification record, alongside the pass kind, the unit rule, and the declared scope; the concrete mechanism that surfaces it to the gate is toolchain-specific and left open below.

**The review unit is not the whole of what the reviewer reads, and the design must say so rather than quietly assume otherwise.** In the merge-time case the same person, in the same sitting, also reads the functional diff. The consolidation bound governs the consolidation commits alone, so a bound-compliant realignment attached to a large functional change still exhausts the reviewer — and the single-budget position is violated by a design that notices only half the load. Three consequences, all settled:

- the functional diff's volume is **not** counted against the consolidation bound (they are different judgements, and mixing them would make the cap unreadable);
- a pull request whose functional diff is itself large **moves its realignment out** — the realignment becomes a standalone pass under the no-host-PR case rather than riding along. What counts as "large" is a threshold, calibrated with the rest of the review budget rather than invented; it is named among the open questions;
- where a realignment does ride along, the consolidation volume admissible in that unit is the **residual** budget after the functional diff, not the full cap. This matters at exactly one place in the design — the split of an oversized realignment, below — and stating it is what stops "the portion that fits" from being computed against a denominator the reviewer does not actually have.

**The declared scope of a pass.** The set of classifiable units the pass commits to examining — normally a set of whole files, and, where a single file alone would exceed the bounds of a review unit, an explicitly enumerated subset of one file. It is stated in the header of the classification record alongside the declared unit rule, and it is what the coverage check counts against. Coverage is a claim about the declared scope, never about the file system.

**The classifiable unit.** The smallest thing a classification entry refers to. It has no *global* definition, because document structures differ and source files differ from prose; it is fixed **per pass** by the unit rule the pass declares in its record header.

Two properties of the unit rule are settled, and the design does not work without either:

- **The rule is drawn from a closed, machine-evaluable set, not written freely.** The coverage check counts classifiable units according to the declared rule; a script can only count under a rule it can evaluate. "The declared rule makes the check implementable regardless of which rule is chosen" is false for a free-form rule, and the deliverables must not repeat it. The requirement is therefore: the toolchain publishes a **closed enumeration of supported unit rules**, each with a counting implementation, and a pass declares one of them by name. Illustratively — and these are illustrations of the *category*, not a fixed list — a Markdown block-level element, a comment block, a single comment line, a numbered list item. Which rules the enumeration should contain is open below; that it is closed and machine-evaluable is not.
- **Choosing the rule is a review-budget decision, not a free per-pass preference.** A coarse rule reduces entry count, reduces spot-check surface, and freezes more redundancy along with frozen content; a fine rule recovers those deletions and raises entry count, removal-judgement count, and spot-check surface — all of which draw on the single review budget. The trade-off is therefore constrained on both sides and must be presented as coupled to the budget rather than as a knob the pass turns at will.

### Artifact taxonomy (the primary intervention)

| Artifact | Function | Lifecycle |
|---|---|---|
| Spec / design doc | **State** | Present tense, describes the system as it is now. No "Revision N" sections. When a business rule changes, the sentence changes. Re-aligned to reality at merge time, not only before implementation. |
| Implementation plan | **Ephemeral** | Has a death date. Marked `status: completed` mechanically at merge; archived later at the author's discretion; **excluded from all retrieval channels** once archived — indexes, globs, knowledge graph, unrestricted full-text search of the tree, **and inbound references from surviving documents**. |
| ADR | **Append-only log** | One file per decision. **The body is immutable; `status` is the single mutable field** — `accepted \| superseded-by ADR-NNN`. All historical rationale that currently pollutes specs belongs here. |
| Code comments | **State** | Explain why the code is the way it is *now*. Never "fix for bug #1234" — that is a commit message, already in git. |

**The ADR immutability carve-out is explicit because the two properties collide.** An artifact cannot be immutable and carry a status field that changes on supersession. The resolution: the body — the decision, the context, the rationale, the consequences — is never edited; the `status` field is the one line the supersession step rewrites, and that rewrite is a mechanical operation, not a consolidation. State the carve-out rather than leaving a reader to discover that the taxonomy's own row contradicts itself.

**Mechanical status marking is exempt from the separate-commit rule — for plans and for ADRs alike.** Marking a plan `completed`, and rewriting an ADR's `status` on supersession, remove nothing, require no judgement, and produce one-line diffs. Applying the consolidation isolation rule to either would be ceremony. State the exemption for both, not only for plans: the isolation rule governs edits that **remove content on the strength of a judgement**, and mechanical status marking is neither.

**Reconciliation of merge-time realignment with the separate-commit rule.** "Re-aligned to reality at merge time" and "consolidation is always a separate commit, never mixed with functional changes" are reconciled as follows: the realignment is **a separate commit inside the same pull request** as the functional change. Same PR, distinct commit, independently readable diff. State this resolution explicitly in the deliverables rather than leaving the reader to infer it.

**Consolidation without a host PR.** The merge-time case is not the only one. A consolidation triggered at the start of brainstorming (see *Triggers*) has no functional change to accompany and therefore no host pull request; it stands alone as its own commit and, where the workflow requires review, its own pull request. The invariant is *never mixed with functional changes*, not *always inside a feature PR*. Say this explicitly, because the same-PR reconciliation above otherwise reads as a requirement to find a host PR that does not exist.

**An oversized merge-time realignment cannot satisfy both rules unchanged, and the resolution has a cost that must be stated.** A pass exceeding either part of the bound is split across review units; a review unit in the merge-time case lives inside one pull request; therefore an oversized realignment cannot all ride in the host PR. The resolution: **the portion that fits — measured against the residual budget after the functional diff, not against the full cap — rides in the host PR as its own commit, and the remainder becomes one or more standalone passes.** The cost, which the deliverables must state rather than gloss: the spec is knowingly left **partially realigned** to code that has already merged, and — per the subset-pass rule — carries **no verification marker** in the interim. Tracking that outstanding remainder is an open question below. Do not resolve this by raising the bound, and do not resolve it by mixing the realignment into the functional commit.

### Positions already settled — treat these as decided, do not re-litigate

#### On comments and the regenerability test

- The source of truth about *what the system does* is **the code itself**, not the comments. Comments can lie, and are the only artifact in the repository that can lie without immediate consequence — no test breaks. Comments must therefore be **compacted, not annotated**: they should carry only current truth.
- The operational rule for comments is not "keep comments true" but **"reduce the surface of what can lie."** A comment that restates the code must be **deleted, not compacted** — it adds nothing and can diverge. This category is large in AI-assisted codebases, because models comment generously by default.
- The bright line for "restates the code" is **regenerability**: if the comment could be reconstructed from the signature, the identifiers, and the control flow alone, it is redundant and is deleted. If reconstructing it would require knowing something not present in the file, it is not redundant, however obvious it looks. This test exists because "looks redundant" is exactly where an LLM misjudges — a one-line comment stating an invariant reads like a restatement.
- **The test must name its reconstructor, because the answer changes with it, and the reconstructor is not the agent.** "Reconstructible from signature, identifiers, and control flow" describes something an LLM holding the whole knowledge graph can do cheaply and a human cannot. The standard is therefore fixed as: **a competent engineer unfamiliar with this module, reading only this file, with no graph and no search.** Not the agent performing the pass; not a reader with repository-wide context. Without this fixed, the test silently optimizes the repository for the agent and degrades it for the person paged at 02:00 — and the deletion is invisible in review because the reviewer, who does have context, can also reconstruct it.
- **The conservative reconstructor shrinks the comment skill's expected yield, and the deliverables must say so rather than let the skill be sold on volume.** Under this standard, most comments in a codebase with mediocre naming are *not* regenerable, so the deletion authority the skill exercises collapses toward the trivially tautological. This is the correct outcome — the asymmetry below demands it — but it is also a prediction about return that belongs next to the prediction about demand, and it is one of the things the observation window should confirm or falsify.
- **Every deletion made on regenerability grounds records its basis.** The classification entry for a deleted comment names what reconstructs it — which signature, which identifiers, which control-flow structure — **and does so against the reconstructor standard above**. This costs one clause per entry and converts the weakest link in the design from an unexaminable judgement into a spot-checkable claim: a reviewer can read the basis and the `-` line together and disagree. An entry whose basis amounts to restating the comment is not a basis and fails review.
- Only comments carrying what the code cannot say about itself survive: the reason for a non-obvious choice, an external constraint (illustratively: SAP B1 / Service Layer behavior, a TwinCAT quirk), a rejected alternative and why, an invariant not expressible in the type system. This category must be **defended conservatively** during consolidation. The failure modes are asymmetric: keeping one redundant line costs tokens, deleting one genuine invariant costs a defect.
- Historical bug-fix references in comments are not to be compacted but **relocated** — to a commit message or an ADR.
- **A comment that disagrees with the code is not automatically a stale comment.** The agent can observe divergence; it cannot determine which side is wrong, because it cannot distinguish intended behavior from a defect. Divergence is therefore **escalated as a suspected defect**, never silently resolved by rewriting the comment to match the code. Without this rule, the comment-consolidation skill launders bugs into documentation, and the laundering is invisible in review precisely because the resulting comment is accurate about the code.
- **In a code-comment pass, the `not verifiable` bucket has no in-file carrier, and none is to be invented.** A source file has no front matter and no place for a `## To be confirmed` section, and per-comment meta-annotation is prohibited outright. The resolution: a comment classified `not verifiable` is **left in place, byte-for-byte unmodified**, and the escalation travels entirely through the out-of-file channels — the classification record for the pass and the escalation intake below. This is a deliberate asymmetry with document passes, where the same bucket lands in a `## To be confirmed` section visible to the next reader of the file. Its consequence is that an unverifiable comment is invisible to anyone who opens the file, which weakens escalation for the very skill most likely to run first; that consequence is recorded as an open question rather than patched with an annotation.
- **The intake, not the file, is what gives a comment pass memory, and this is what makes repeated passes idempotent.** Because a frozen comment carries no marker, a later pass over the same file re-encounters it, re-judges it, and — absent a rule — re-escalates it. The rule: the escalation step **reads before it appends**, and an entry is appended only where no entry in a suppressing state already exists for the same unit reference and entry kind. Without this, the intake accumulates duplicates proportional to how many times a file has been passed over, and the observation window's first evidence about how often the outer tier fires is inflated by re-runs rather than measuring anything.
- **Read-before-append is inert without a churn-stable unit reference, and this is a hard requirement rather than a detail.** Unit references are structural or positional — block *N*, comment line *N*, a heading path. Consolidation itself shifts them, and so does every unrelated edit to the file. A dedup key built on a reference that moves will both fail to suppress genuine duplicates and falsely suppress new observations about different content. The intake's unit reference must therefore be **stable under file churn** — anchored to content or to a durable identifier rather than to position — and the deliverables must state that requirement even though the concrete scheme is toolchain-specific and open below. This is load-bearing: the intake is the design's only memory, and an intake whose keys drift has no memory at all.
- **Freezing happens at the declared unit, and it applies to both frozen labels.** A unit labelled `not verifiable` **or** `contradicts code → suspected defect` is preserved whole, including any regenerable lines inside it; the pass does not reach into a frozen unit to compact part of it. A coarse unit rule therefore freezes redundancy along with the frozen content. A pass that needs finer resolution declares a finer unit rule — a single comment line rather than a block — and accepts the higher entry count and the larger spot-check surface that follows, which is a claim on the review budget rather than a free choice. Do not present the freeze as a defect to be engineered around: it resolves in the cheap direction of the standing asymmetry, since a frozen redundant line costs tokens while reaching into a frozen unit risks the deletion the label exists to prevent.

#### On the classification labels themselves

- **Exactly one label per classifiable unit, because the coverage count depends on it.** A count of entries against a count of units is only meaningful if the mapping is one-to-one.
- **A unit can genuinely satisfy more than one label, so a precedence order is mandatory rather than a nicety.** A stacked revision note is both obsolete as state and historically meaningful; a contradicting statement may also be unverifiable. Absent a tie-break, the label is whichever the agent happened to reach first, and the classification becomes non-reproducible while the count keeps passing.
- **The order runs from most conservative to least, and the first match wins:**
  `contradicts code → suspected defect` **>** `not verifiable` **>** `historical decision → ADR` **>** `obsolete` **>** `still true`.
  Freeze before escalate, escalate before relocate, relocate before delete. State the order and state its rationale: every step down the list transfers more authority to the agent, so the tie-break must resolve upward.
- **The precedence order deliberately over-reports into the suspected-defect channel, and the intake must be able to absorb that.** A unit that is both unverifiable and apparently divergent from the code is labelled a suspected defect, even though the agent cannot establish that the statement is wrong rather than merely unconfirmable. This is the right resolution — it resolves upward — but it routes arbitration requests into the channel with the most expensive consumer. The consequence, which is settled: the intake supports **reclassification of an open entry between kinds by its consumer**, and a reclassification updates the existing entry rather than appending a new one. Without that, resolving upward silently converts a taxonomy choice into noise in the defect queue.

#### On the `## To be confirmed` section — its grounds, and its lifecycle

- **The exception is on state-versus-open-work grounds, not on metadata grounds, and getting this right matters downstream.** A `## To be confirmed` section is not per-paragraph verification metadata and does not violate that prohibition at all; calling it "the sole exception to the no-per-paragraph-metadata rule" is a category error that muddles the very distinction the open question about in-file comment markers has to rule on. The rule it genuinely excepts is *documents describe current state only*: open work assigned to a person is not current state, and it earns its place in the file because the next reader must see it. State the grounds this way.
- **The section is open work, and open work is resolved by deletion.** A person rules on an item, and the item then either becomes a sentence in the body (it was true), moves to an ADR (it was a decision), or disappears (it was neither). It is never re-labelled, never annotated with its resolution, and never kept as a record of having once been uncertain — that record is the intake entry and the commit message.
- **A subsequent pass over the same document treats existing items as classifiable units, with a defined label rather than an unstated one.** An unresolved item is labelled `not verifiable` and frozen; the pass appends nothing to the intake where a suppressing entry already exists. A resolved item that a person has already actioned is removed, and that removal counts against the review unit's line cap but is **not** a removal judgement of the kind the judgement cap counts — nobody is being asked to accept the agent's reasoning, only to observe that a person already ruled. Stating the label matters: "counted and classified" without saying as what leaves the freeze rule undefined for exactly the content most likely to recur across passes.
- **A statement ruled true-but-unconfirmable in the repository would otherwise loop forever, and the intake's terminal states are what break the loop.** A person rules an item true; it becomes a sentence in the body; the next pass classifies that sentence `not verifiable` and returns it to the section. Since the design forbids per-paragraph metadata, nothing in the file can record that a ruling was made — so the suppression must live in the intake. Entry states are therefore three, not two: `open`, `resolved-actioned`, and `resolved-confirmed-external`. The last is terminal and **suppresses re-escalation of the same unit indefinitely**, which is what makes repeated passes over genuinely external content converge instead of oscillating. Without it, the intake's open set grows monotonically with the amount of legitimate tier-3 content in the repository, and the first evidence about how often the outer tier fires is dominated by permanent residents.
- **A section that survives several passes unresolved is a finding about the intake's consumer, not a reason to let it grow.** The design's one sanctioned in-document carrier is the one place the append pathology can reappear, and it reappears exactly when nobody is consuming the intake. Say so, and treat the growth as the signal it is.
- **The caps govern removals, not additions, and this asymmetry is accepted deliberately rather than by omission.** Items added to a `## To be confirmed` section are added lines a reviewer must read, and no cap governs them. The design accepts this on the grounds that each item is open work assigned to a person and that unresolved growth is itself the diagnostic signal above. State the asymmetry explicitly, because leaving it unstated makes the one place the pathology can return look like the one place nothing was thought about; whether added-line volume needs its own ceiling is open below.

#### On the bounds that make diff-based review real

- **Because the regenerability test is the weakest link, the volume it is applied to must be bounded.** The test is fallible in exactly the direction that costs a defect, and the only control on it is a human reading `-` lines. A consolidation whose removed content exceeds what a reviewer will actually read has no control at all — the diff-based review guarantee is nominal.
- **The bound on a consolidation review unit has two parts, because two different things exhaust the reviewer.** Reading volume is exhausted by removed lines; judgement volume is exhausted by the number of independent removal judgements the reviewer must be willing to accept. These do not move together: one forty-line removed block is one judgement, while forty removed one-line comments are forty, and a line-only cap treats them as equivalent. Every consolidation review unit therefore carries **both** a cap on removed lines **and** a cap on independent removal judgements. A pass may breach neither. Both numeric values are to be calibrated by observation and must not be invented in the deliverables.
- **Call it a removal-judgement cap, not a deletion-judgement cap, and define its countable set once.** The two terms were used interchangeably and the difference is load-bearing, because the countable set includes a label that relocates rather than deletes. The countable set is: **entries labelled `obsolete`, entries labelled `historical decision → ADR`, and entries recording a regenerability deletion.** Defining the cap against the regenerability basis alone would make it bind on comment passes and go nearly slack on prose passes, where removals are authorized by an `obsolete` label and carry no regenerability basis at all — leaving judgement volume effectively unbounded in exactly the pass type where a single deleted paragraph can cost the most. That would be a single-quantity bound wearing two labels, which this design refuses elsewhere.
- **An ADR relocation is counted, and it is not counted at a discount.** Verifying a relocation requires the reviewer to read two diffs — the removal from the source and the addition to the ADR — and to judge the transfer faithful. It therefore costs *more* reviewer attention than a plain deletion, not less. Do not present relocation as the cheap case; whether it should carry more than unit weight in the cap is a calibration input.
- **Both parts of the bound are scoped to the review unit, not to the commit, and splitting does not raise them.** Review capacity is a property of the human reading the pass, so a bound enforced per commit is evadable by arithmetic: four commits of two hundred removed lines each satisfy a two-hundred-line per-commit cap and still present the reviewer with eight hundred lines. A pass that would exceed either part is therefore **split across review units** — separate PRs, or separate passes on separate days — not across more commits inside the same one, and not across concurrent sub-agents. Subdividing into multiple commits within a review unit remains encouraged for diff readability and remains subject to the same totals.
- **Every consolidation-class commit in the unit counts against the totals, including the severance commit.** Inbound-reference severance removes lines from live documents on the strength of a judgement, so it is consolidation for the purposes of the cap. A design that exempted it would let the one mechanism it calls low-risk carry unbounded deletions.
- **A record commit is consolidation-class for identity and contributes zero to both caps.** Where the committed-record channel is used, the record file is committed **in its own commit inside the review unit**, never inside the consolidation commit — otherwise the consolidation diff contains something other than consolidation, which is the property that makes it reviewable. The record commit removes nothing and authorizes nothing, so it adds no lines to the removal cap and no entries to the judgement cap. State this, or the requirement to keep the record out of the consolidation commit and the requirement to materialize it inside the review unit read as mutually exclusive.
- **The bound applies to every consolidation review unit, not only to comment passes.** Its justification is review capacity, and review capacity is a property of the human, not of the artifact type: a spec consolidation that removes eight hundred lines is exactly as unreviewable as a comment consolidation that removes eight hundred lines. Whether the *numeric values* should differ by pass type — removed prose and removed comment lines are not equally dense — is deliberately left open below. The bound is a review-capacity constraint, not a quality metric.
- **The bound and the spot-check draw on the same budget and are calibrated as one decision.** The bound exists because a human must read the `-` lines and accept the removal judgements; the entry spot-check (see the consolidation procedure) exists because reading `-` lines does not detect skimming. All of it consumes the attention of the same reviewer in the same pass, so any of the numbers chosen without the others defends nothing: raising one silently degrades the others. The deliverables must present the review budget of a unit as **one quantity with four claims on it** — removed lines to be read, removal judgements to be accepted, entries to be spot-checked, and, in the merge-time case, the functional diff sharing the same sitting — and must state that the numbers are calibrated together or not at all.
- **The bound is the one control that cannot be placed before the step it authorizes, and the deliverables must state the exception rather than let it be discovered.** Removed lines and removal judgements do not exist until the rewrite has happened, so bound enforcement is structurally a post-hoc gate. This is a real exception to the ordering principle stated for the coverage check, and it has a consequence: on failure, the rewrite already exists, which creates precisely the pressure to reconcile the check to the work that the ordering principle exists to prevent. Two mitigations are settled. First, the **admissible remedies on bound failure are enumerated in advance** — split the pass across review units and re-run, or discard and re-scope — and *raising the cap, redistributing across more commits inside the same unit, and fanning out across agents are not among them.* Second, the pass **projects its volume before rewriting**: the classification record's removal-authorizing entry count is known at the end of the classification pass, so the judgement cap can be checked pre-rewrite, and only the removed-line count genuinely requires the rewrite to exist. State the split: the judgement half of the bound is a pre-rewrite gate; the line half is a post-rewrite gate with enumerated remedies.
- **Enforcement must run at a gate that can see the whole review unit.** A pre-commit hook cannot see a pull request, so in the merge-time case a pre-commit hook is insufficient by construction: it can only ever enforce a per-commit total, which is the evadable bound this design rejects. Enforcement therefore runs at whatever gate observes the complete unit — a PR-level check in the merge-time case, a pass-level check reading the review-unit identity from the classification record header in the standalone case. Specify the requirement; the concrete gate is toolchain-specific and left open below.
- **A gate can only read committed content, so the record must exist in a gate-readable form inside the review unit.** This is the hinge that makes the mechanical checks real rather than nominal, and the deliverables must state it: a classification record that lives only in the author's working tree can satisfy the **local, pre-rewrite** coverage check and nothing else — a PR-level or pass-level gate cannot see it. Every pass must therefore materialize the record inside its review unit through **one of exactly two channels**:
  1. **rendered into the commit message body in a fixed machine-readable format** — which makes that body a parsed contract, not merely human-readable prose, and constrains the format accordingly; or
  2. **committed as a file that is excluded from every retrieval channel** (see *On retrieval exclusion and deletion*), in its own commit within the review unit.
  Which of the two a given toolchain supports is left open below. That one of them is mandatory is settled, and a pass that materializes neither has no enforceable bound and no gate-verified coverage, whatever it claims.
- **The gate recomputes; it does not read the agent's arithmetic.** A gate check that compares the entry count asserted in the record header against the entry count in the record body verifies internal consistency and nothing else — both numbers come from the controlled party. The gate must therefore **recount classifiable units itself**, from the repository at the declared baseline sha, under the declared unit rule, within the declared scope, and compare that to the entries present in the record. State this explicitly; it is the difference between a mechanical check and a well-formed self-report.
- **The declared baseline sha needs its own floor, or the whole count is taken against a state of the agent's choosing.** Scope, unit rule, and baseline are all agent-declared, and the target-set cross-check floors only the first two. The gate therefore additionally verifies that the declared baseline **is an ancestor of the review unit's consolidation-class commits and is the parent of the first of them** — which in the merge-time case is the functional commit, exactly as the isolation ordering requires. A baseline that fails this test invalidates the pass; it is not a warning.
- **The target set the cross-check compares against must not arrive by way of the agent's narration.** A cross-check fed a target set the agent reported is two self-reports compared to each other. The target-set selection script's output — together with the graph build state — is therefore either **committed inside the review unit** alongside the record, or **re-run by the gate itself**. Which of the two a toolchain should prefer is open; that the compared-against side must be non-agent-authored is settled, since that is the entire basis on which the cross-check is credited as a floor.
- **The three tiers are a partition of authority, not an independent control on the regenerability test.** Tier assignment is itself a judgement the agent makes before it knows the answer: it cannot know a comment states external truth until it has already decided the comment is not regenerable. A deleted regulatory constraint *is* a tier-3 item misclassified as tier-1, so the tier table cannot be presented as the safety net that catches regenerability errors — it is the same judgement wearing different labels. The only controls genuinely independent of that judgement are the two-part bound and the citation-plus-spot-check. State this in the deliverables wherever the tier table appears, or the table will be read as protection it does not provide.

#### On plans

- Implementation plans are **archived, not deleted** — but archived plans must be invisible to retrieval. A readable archived plan is worse than a deleted one: it carries the authority of a spec and the content of an intention.
- Plan status marking (`completed`) happens **at merge, immediately**; physical archiving happens **later, at the author's discretion**. These two events are deliberately decoupled. The reason: between merge and archiving, a live plan saying "I will do X" coexists with a spec saying "the system does Y", and if implementation diverged from the plan (it always does), the agent has two sources in conflict and no criterion for preferring one. The status field supplies the criterion at zero cost, independently of when the file physically moves.
- **The archiving script owns the archived-plan inventory.** Once a plan is excluded from the knowledge graph, the graph can no longer be queried to find plans that were archived but never status-marked, or status-marked but never archived. That reconciliation is therefore a responsibility of the archiving script, which maintains its own record of what it moved and when — it is not a knowledge-graph query and must not be specified as one.
- **The same reasoning extends to excluded documents, and the exclusion script owns that inventory.** Phase-one exclusion is only meaningful if phase two — delete later if nothing missed it — can find the set awaiting the decision, and an excluded document is by construction invisible to the graph that would otherwise list it. The exclusion script therefore maintains its own record of what it excluded, when, and which inbound references were severed. Without it, "delete later" is a decision nobody can enumerate the subjects of, and the severed-reference set needed for recovery is lost.
- **The inventory is updated by the severance step regardless of who performs it.** In the first shipment the severance is human-executed while the exclusion configuration is scripted, so an inventory written only by the script would be missing the severed-reference set during exactly the phase in which the design says a human does the severing — losing the recovery data at the moment it is most likely to be needed. Specify the inventory as an artifact with a mandatory update step attached to the severance itself, not as a side effect of the script.
- If, at the end of a feature, the plan contains information that would be painful to lose, that information belonged in the spec or in an ADR and never made it there. It is a signal about a missed transfer, not a reason to keep the plan alive. The correct response is to move the content to its proper artifact, then let the plan die on schedule.

#### On markers

- **Default is implicit:** unmarked content is current. Annotating a paragraph as "still true" is noise that ages worse than the content itself — a six-month-old `verified: true` is a false claim wearing a guarantee.
- **No meta-annotation inside code comments, ever.** A comment describing the verification status of another comment is the bottom of the barrel.
- The only persistent marker worth defending is per-document, not per-paragraph: `last-verified-at: <commit-sha>` in the front matter. It costs nothing, ages informatively rather than deceptively (a sha 400 commits behind is a real signal; a stale `verified: true` is a lie), and gives the agent a signal about how much to trust the file. It applies to documents whose format carries front matter; **a document whose format cannot carry it is treated like a source file — no marker, and no marker invented for it** — which is consistent with the prohibition above.
- **The sha recorded in `last-verified-at` is the commit the document was verified *against*** — the repository state the agent read while classifying, i.e. the `HEAD` in effect at the start of the classification pass — **not the consolidation commit that writes the field.** Recording the consolidation commit would be circular: its sha does not exist until after the file has been written. This resolution matters because the field's whole value is as a distance measure against the code, and the code state that was actually examined is the parent, not the child.
- **The recorded sha must remain resolvable in the integration branch after merge.** A sha the reader cannot resolve is not a weaker distance measure, it is the same class of lie as a stale `verified: true` — and in the merge-time case the baseline is a feature-branch commit, which a squash or rebase merge destroys. The field is therefore only admissible where the toolchain and merge strategy guarantee resolvability, or where a mechanical post-merge step maps the recorded sha to a surviving one. Which of those applies is toolchain-specific and left open below; what is settled is that a dangling sha is not an acceptable outcome and that the field is omitted rather than written unresolvable.
- **`last-verified-at` is written only by a pass whose declared scope is the whole document.** A subset pass — one that consolidated part of a file because the file alone would exceed the bounds — does not write the field, because writing it would assert verification of content the pass never examined. This follows directly from the requirement that a control measure the property it is credited with: a `last-verified-at` that means "most of this file was checked" is the same class of lie as a stale `verified: true`. The corollary is that a document consolidated across several review units carries no verification marker until the last of them completes, and that the tracking of the outstanding remainder is an open question below — deliberately not solved by inventing a partial-verification marker.
- **Isolation by commit is mandatory whenever the pass realigns a document to a functional change; stashing is admissible only for a standalone pass.** The two are not interchangeable, and the baseline resolution above is what decides it: if the functional work is stashed rather than committed, the captured `HEAD` predates the change the document is being realigned to, so the agent verifies the document against code that does not yet contain the behavior in question — the exact failure the fixed ordering exists to prevent. It is also what the gate's ancestry check requires, since a stashed change leaves no commit for the baseline to be the parent of. Commit the functional work first in the merge-time case. Reserve stashing for a brainstorming-time consolidation that happens to have unrelated work in flight, where the captured `HEAD` and the tree the agent reads coincide.

#### On retrieval exclusion and deletion

- **Retrieval exclusion is the primary lever; deletion is the secondary one.** The same mechanism that makes archived plans invisible to retrieval works on any low-value document, at far lower risk and with no unrecoverable step. Deletion's marginal gain over exclusion is small; its downside is unrecoverable. Deletion is therefore a **two-phase operation**: exclude from retrieval first, delete later if nothing missed it.
- **Exclusion is only as strong as its weakest channel, and unrestricted full-text search is a channel, not a residual.** An excluded file remains reachable by direct path from cross-references in surviving documents, and remains findable by a full-text search of the working tree. Phase one is therefore **exclude *and* sever inbound references**, and the channel list is: retrieval index, glob patterns, knowledge graph, inbound links from documents that remain in play, and the scope of any search tool the agent routinely uses. The earlier position that tree-wide search reachability is an accepted residual is **too weak to survive contact with how agents actually work**: where the agent's toolset includes unrestricted grep over the tree, that is not a corner case, it is the primary retrieval path, and an exclusion that does not constrain it captures little of the claimed benefit. The correct statement: reachability by a *deliberate* human search of the tree is accepted residual and is not a reason to prefer deletion; reachability by the agent's routine search tool is a channel that must be closed, and where the toolchain cannot scope that tool, the exclusion cost claim is conditional and must be stated as such.
- **Exclusion is recoverable, but not costlessly, and the deliverables must not overstate this.** Restoring an excluded file is a configuration change; restoring the inbound references that were severed is a revert against documents that have themselves been edited since, so the recovery cost rises with elapsed time and with the churn of the severed documents. State the property as *no unrecoverable step, with recovery cost rising after the fact* — not as *no irreversible step*. The comparison with deletion still favors exclusion decisively; the margin is just smaller than an unqualified claim suggests.
- **Phase two has no trigger unless one is defined, and the deliverables must not present a two-phase operation whose second phase floats.** "Delete later if nothing missed it" requires a defined signal for *missed it* — and the excluded document is by construction invisible to the graph that would otherwise report a dangling reference. Two consequences are settled. First, the exclusion inventory is the only enumeration of the candidate set, so phase two is a review of that inventory and nothing else. Second, in the absence of a defined miss signal, the correct default is **exclusion is permanent and phase two never runs**, which costs a retained file nobody retrieves and forfeits almost nothing, since the benefit was captured in phase one. What constitutes evidence that nothing missed an excluded document is open below; that the design does not depend on the answer is settled.
- **Severing inbound references is a destructive edit on documents that stay in play, and is governed as one.** It removes lines from surviving specs and docs, so it is a separate commit, it counts against the bounds of its review unit, and it is reviewed by reading the `-` lines like any other consolidation. Treating it as a side effect of an exclusion script — invisible, uncapped, unreviewed — would put unreviewed deletions into live documents through the one mechanism this design describes as low-risk. That review is mandatory is settled; whether an agent may *perform* the severing autonomously at all remains open below, and the first shipment is scoped accordingly under *Recommended sequencing*.
- **A severance pass carries a classification record like any other consolidation pass, and its floor is the exclusion inventory.** Since its removals count against the caps and the gate accumulates over every consolidation-class commit in the unit, a severance without a record is a set of removals in a currency the gate cannot count. The record's shape for this pass kind is fixed: **pass kind `severance`; unit rule "one inbound reference occurrence"; declared scope the set of surviving documents holding references to the excluded target; one entry per severed occurrence.** The non-agent-authored floor under its declared scope is the exclusion inventory's enumeration of inbound references, not the knowledge graph — which cannot see the excluded target. Its entries count against the removal-judgement cap.
- **The exclusion machinery has a second, non-destructive use.** It is the mechanism that lets a record be kept in the repository without being kept in the context: committed, versioned, reachable by a human who goes looking, invisible to retrieval. This is what makes an oversized classification record storable rather than forcing a choice between a commit message that cannot hold it and a scratch file that discards it. Present exclusion as a general lever for separating *retained* from *retrievable*, not solely as a disposal step.
- **A newly committed record is created outside retrieval; it has no inbound references to sever.** Where the classification record is materialized as a committed file, the exclusion step is *configuration only* — the file is born with nothing linking to it, and specifying "sever its inbound references" would be an instruction with no referent. The pointer in the commit message is not an inbound reference in the relevant sense, because commit messages are outside retrieval by construction. State this, because the general exclusion procedure and this particular use of it differ in exactly one step.

### Rules vs. skills — the split to encode

These are not alternatives. **Rules prevent accumulation; skills repair what accumulated anyway.** Rules alone leave the pre-existing debt untouched (they do not apply retroactively); skills alone condemn the project to perpetual maintenance.

The assignment criterion is mechanical: a directive belongs in a **rule** if it must apply *always, at zero activation cost*; it belongs in a **skill** if it is a *rare, multi-phase procedure with risk of information loss*; it belongs in a **script or hook** if a shell command could do it.

**Rules** (`CLAUDE.md`, deliberately kept under ~20 lines for this domain — a 300-line `CLAUDE.md` is no longer a rule set, it is documentation the agent dilutes):

- the artifact taxonomy;
- the no-append rule on specs, **stated with its justification** ("history lives in git and in ADRs") — the justification is what makes the agent willing to overwrite;
- the comment policy: only what the code cannot say about itself; no bug-fix references, **stated with its justification**;
- the implicit default: unmarked = current;
- the obligation to **flag rather than rewrite** anything that is no longer verifiable;
- **the location of the escalation intake.**

**The intake's location is a rule line, not an implementation detail.** The flag-rather-than-rewrite obligation is inert if the agent has to guess where the flag goes, and a rule that resolves to a guess is a rule that resolves differently every session. It costs one line. Account for it in the budget explicitly, rather than shipping five rules and an implicit sixth.

**How the taxonomy fits the line budget, shown rather than asserted.** Four artifacts, six rules and two justifications do not fit in ~20 lines if the taxonomy is reproduced with its lifecycle rules. In `CLAUDE.md` the taxonomy is therefore **one line per artifact, function plus a lifecycle keyword only** (state / ephemeral / append-only / state), with a pointer to the project overview for the lifecycle detail. The full table lives in the overview and is not duplicated in the rule set. The deliverables must show the arithmetic, not claim it:

| Rule-set line | Lines |
|---|---|
| Taxonomy, one line per artifact | 4 |
| No-append rule on specs | 1 |
| — its justification | 1 |
| Comment policy | 1 |
| — its justification | 1 |
| Unmarked = current | 1 |
| Flag rather than rewrite | 1 |
| Escalation intake location | 1 |
| Pointer to the overview for lifecycle detail | 1 |
| **Total** | **13** |

Treat the line budget as binding and the taxonomy rule as a compressed index, not as an explanation. The remaining headroom is deliberate slack, not an invitation.

**Scope of the justification requirement.** The line budget does not accommodate a justification on every rule, and attaching one to all of them would break the budget. Justifications are attached to the **two rules the agent will otherwise rationalize its way around** — the no-append rule and the comment policy — because both ask the agent to destroy information. The remainder are declarative and self-enforcing. Do not treat "rules carry their justification" as a universal that conflicts with the line budget; treat it as targeted.

**The flag-rather-than-rewrite rule requires an intake, and the intake ships with the rules.** A rule that obliges the agent to flag is inert if there is nowhere for the flag to land: flags accumulate in transcripts, nobody owns them, and within two sessions the rule has trained the agent to produce output that is discarded. The intake is a **convention plus a location** — a single append-only destination for suspected defects, unverifiable statements, and observed obsolete-citation events, with the minimum fields needed to act on an entry:

- what was observed;
- where — the unit reference, **in a form stable under file churn**, per the settled position above;
- the originating context — the pass that produced it, or the session in which it was noticed;
- **the sha in effect when the observation was made**, which exists for all three entry kinds (the verification baseline for a pass; the working `HEAD` for an in-session observation) and is therefore required rather than conditional;
- the entry's state — `open`, `resolved-actioned`, or `resolved-confirmed-external` — which is what makes read-before-append implementable and what stops legitimately unverifiable content from re-escalating forever;
- **for a resolved state, the sha at which the ruling was made**, distinct from the observation sha above. This is required for the same reason `last-verified-at` records a sha rather than a boolean: a terminal `resolved-confirmed-external` is a durable statement that a person once ruled a unit acceptable, and without a date attached to a repository state it becomes precisely the stale `verified: true` this design refuses — relocated out of the file, where it is harder to notice. With the ruling sha, a suppression 900 commits old is a visible signal that the suppression may no longer hold;
- the entry kind, which the consumer may **reclassify in place** rather than by appending a new entry.

It is not a skill and not a rule; it is a file convention and, at most, a script that appends to it — **and that script is idempotent on `(churn-stable unit reference, entry kind)` against all non-suppressed states**, per the settled positions above. An append-only log without a dedup rule accumulates duplicates in proportion to how often a file is passed over, which corrupts the one measurement the observation window produces.

**The intake's shape is settled; only its path, its format, and its churn-stable reference scheme are open, and that is deliberately not a blocker.** Read the open questions below as a request to *choose* a path, a line-oriented or key-value format, and a reference scheme in the target toolchain — not as an admission that the intake is undesigned. Its destination cardinality (one), its append-only discipline, its three entry kinds, its three states, its required fields, its reclassification-in-place rule, and its idempotence rule are fixed above. Shipping the rules therefore requires decisions that take hours, not a design that does not exist. Do not read the sequencing advice further down as blocked on an unresolved question.

**Skills — exactly two.** The division criterion is *not* the artifact type, and it is *not* that one skill deals in local truth while the other deals in external truth — both encounter external truth. It is **what external truth does to the pass**:

1. **Comment consolidation.** What the agent verifies autonomously is **redundancy and obsolescence, against the code, inside the repository**: read the function, compare the comment, delete the regenerable, collapse stacked notes, relocate bug-fix references. But the category the skill exists to *preserve* — an external constraint, an invariant not expressible in the type system — is by definition not verifiable in the repository, so this skill meets tier-3 content routinely rather than exceptionally. For this skill, external truth is a **stop condition**: the unit is frozen byte-for-byte, escalated through the intake, and the pass moves on. It never becomes work the pass has to finish. That is what makes the skill largely autonomous — not a local truth source. It may **not** decide autonomously when comment and code disagree; that escalates. Per-file or per-module scope, output verifiable by reading the diff, little human judgment required per pass — **subject to the two-part bound per review unit and to the per-deletion regenerability basis**, without which "verifiable by reading the diff" is a claim rather than a control.
2. **Spec and design-doc consolidation.** Truth source: the code **plus** business rules that live outside the repository, and here external truth is **work to be arbitrated**, not a stop condition. The agent cannot close the loop alone. It produces the exhaustive classification, rewrites what is verifiable, and hands over a `## To be confirmed` section that a person must rule on before the pass completes. Low volume, high risk, human arbitration mandatory.

**"High-volume" is the wrong word for the comment skill, and the deliverables must not use it.** Autonomy per pass is not throughput in aggregate. Both skills are bounded by the same single review budget, so neither produces more reviewed consolidation per week than the reviewer absorbs; what differs is that the comment pass does not *block* on arbitration while the spec pass does. Combined with the conservative reconstructor standard, whole-unit freezing, and the removal cap — all of which shrink per-pass yield — the comment skill's aggregate return is a measurement question, not a property to assert. State it as: *high autonomy per pass, non-blocking, aggregate return to be measured.*

**Higher automation is not lower risk.** Comment consolidation is the more autonomous skill because external truth stops it rather than blocking it, not because its errors are cheaper. Its characteristic failure — a deleted invariant — is the single most expensive outcome in this whole design, and it is invisible in the resulting document by construction. Do not let the automation gradient be read as a risk gradient in the deliverables; the two skills differ in *who arbitrates* and in *whether arbitration gates completion*, not in *how much a mistake costs*.

**Each skill states its bound, and the bounds are not the same kind of thing.** For comment consolidation the binding constraint is numeric and mechanical: the two-part bound per review unit — removed lines and removal judgements — enforced at a gate that sees the whole unit rather than resetting per commit. For spec consolidation the binding constraint is the mandatory human arbitration step: the pass cannot complete until a person has ruled on `## To be confirmed`, which limits throughput regardless of file size, and the two-part bound applies on top of it as a review-capacity ceiling. Require each skill definition to name its bound explicitly and to say which kind it is. Do not require the numeric part to be the *primary* bound for both; for the spec skill, presenting it as primary would misdescribe what actually limits the pass.

Merging these two into one skill costs twice: irrelevant instructions get loaded (half the procedure never applies), and — worse — the trigger description becomes generic, so the skill fires when it shouldn't and fails to fire when it should. Trigger precision is the real design constraint of skills. Fragmenting into five has the opposite problem: overlapping triggers, arbitrary selection, and loss of the ability to reason about what was actually done.

**Shared machinery, not duplicated prose.** Both skills face the same scoping problem, and the strategy for solving it must live in **one place both skills invoke** — a target-set selection script over the knowledge graph — not as two prose scoping sections inside two skill definitions. Two prose copies of the same strategy drift, and the drift is silent. The skills differ in what they do with the target set, not in how they choose it.

**Neither rule nor skill** — these are mechanical operations that must not consume a context load to perform what `sed` would do:

- marking a plan `completed`, and rewriting an ADR's `status` on supersession → a merge-checklist step or a hook; both exempt from the isolation rule;
- archiving plans, excluding them from retrieval, and maintaining the inventory that reconciles status marking with physical archiving → a script plus retrieval configuration;
- excluding low-value documents from retrieval (phase one of deletion), and maintaining the inventory of what was excluded, when, and which inbound references were severed → the same script and configuration, with the inventory's severance fields updated by whoever performs the severance; the accompanying severance of inbound references is a reviewed destructive edit carrying its own classification record, not a silent script side effect, per the settled positions above;
- target-set selection for both consolidation skills → a single shared script over the knowledge graph, invoked by both, **recording the graph's build state alongside its output**, with that output either committed in the review unit or re-runnable by the gate;
- **coverage verification of the classification pass** → a script that counts the classifiable units **within the pass's declared scope, as they exist at the verification baseline sha**, according to the declared unit rule drawn from the closed enumeration, and compares that count against the number of classification entries the agent produced, failing the pass on mismatch. Counting against the working tree at commit time would be incoherent: consolidation removes classifiable units, so the post-rewrite count is guaranteed not to match an exhaustive classification of the pre-rewrite state. **It runs twice: locally, before the rewrite, as a gate on proceeding; and at the review-unit gate, against the materialized record, as a gate on merge — recomputing the unit count itself rather than reading a count the record asserts.**
- **cross-checking the declared scope, the baseline, and the graph's freshness** → the same script compares the declared scope against the output of the shared target-set selection script and fails the pass in **both** directions: where the declared scope is **narrower** without a recorded bound-driven split reason, and where it is **broader** than the target set, since blanket scope is the named failure mode and an uncaught expansion is how a pass acquires it. It also fails where the recorded graph build state is stale relative to the verification baseline beyond the threshold, because a floor made of stale data is not a floor; and it fails where the declared baseline is not the parent of the first consolidation-class commit in the review unit, because an unfloored baseline lets the count be taken against a state of the agent's choosing. This control exists because scope, unit rule, and baseline are all agent-declared, and a control whose parameters the controlled party sets is self-report wearing a script's clothing;
- **enforcement of the two-part bound** across a consolidation review unit → a check at a gate that observes the whole unit, accumulating removed lines and removal judgements over every consolidation-class commit in it; the judgement half checked pre-rewrite from the classification record, the line half post-rewrite with enumerated remedies; not agent self-restraint, and not a per-commit counter that resets;
- appending an entry to the escalation intake → a script, invoked by either skill, idempotent on `(churn-stable unit reference, entry kind)` against non-suppressed states, supporting reclassification in place, never a hand-written note in chat;
- updating `last-verified-at` → a side effect of a skill, not a skill, and only on a whole-document pass whose recorded sha is resolvable post-merge, per the settled positions above;
- **capturing the baseline measurement the observation window depends on** → a script plus, where the retrieval channels are not introspectable, a defined manual sampling procedure, shipped with the rules, per *Recommended sequencing*.

**The coverage check needs a machine-readable input, and the classification record is that input.** The check cannot read a commit message that does not exist yet, and it cannot count entries in prose the agent narrated in chat. The classification is therefore written, during the pass, to a **structured record at a conventional path in a fixed line-oriented or key-value format**, one entry per classifiable unit. That record is the coverage script's input, the source from which the gate-readable form is materialized, and the thing the human reads alongside the diff. Specify this as a required artifact of the pass with a defined shape; do not specify a format the toolchain has not been observed to support, and mark the format choice and path as open. What must not happen is a coverage check specified against an input that does not exist — that is a control on paper only, and this design has no room for those.

**The record's header declares the six things every check reads.**

| Header field | The check that would be undefined without it |
|---|---|
| Pass kind (`document` \| `comment` \| `severance`) | Which floor applies to the declared scope, and which cap values apply if they differ by pass type. |
| Review-unit identity | The bound cannot accumulate across a unit it cannot delimit. |
| Unit rule, named from the closed enumeration | The coverage count cannot count units without an evaluable rule. |
| Declared scope | Coverage would fail by construction on every split pass if defined against the file. |
| Verification baseline sha | The count would be taken against the wrong tree; and the ancestry check has nothing to floor. |
| Graph build state the target set was derived from | The scope cross-check cannot know whether its own floor is sound. |

What remains open is which unit rules the enumeration should contain, and how the outstanding remainder of a split file is tracked — not whether the scripts can run. A declared bad rule or an implausibly narrow declared scope is visible to the reviewer and, for scope, caught in both directions by the target-set cross-check; an undeclared one is neither.

**Required contents of a classification entry.** Each entry carries: the churn-stable unit reference, the label, and — for any label asserting a fact about the code (`still true`, `obsolete`, `contradicts code`) — the **specific code location or identifier the judgement was verified against**. Deletions on regenerability grounds additionally carry the basis, stated against the reconstructor standard, per the settled position above. This requirement exists because a bare label is producible without reading anything, while a citation is not: it is checkable against the file, and it is what turns a human spot-check of a handful of entries into evidence about the whole pass. Labels alone are not.

**The record is materialized in the review unit; the working-tree copy is transient.** The two channels are named under the bounds section above, and the choice between them is toolchain-specific. Three decision rules are settled. First, **the working-tree copy must not be swept into the consolidation commit** unless the committed-file channel was chosen deliberately — a consolidation diff that accidentally contains the record is no longer a diff of nothing but consolidation. Second, where the committed channel *is* chosen, the record goes in **its own commit** within the review unit, contributing zero to both caps. Third, **where the toolchain cannot reliably keep a transient file out of a commit, choose the committed-and-excluded channel outright**, because its cost is a retained file nobody retrieves and the alternative's cost is a polluted review unit. Uncommitted scratch output is not a third channel; it satisfies no gate.

### The consolidation procedure

1. **Isolate the working tree.** Consolidation is always a separate commit, never mixed with functional changes. The diff must be readable as a semantic diff, which is what makes it reversible. In the merge-time case this means a separate commit within the same pull request; in the brainstorming-time case it means a standalone commit with no host PR. Concretely: bring the working tree to a clean state first — in the merge-time case by **committing** the functional work, never by stashing it, for the reasons given in step 3; in the standalone case by committing or stashing whatever unrelated work is in flight — so that the consolidation diff will contain nothing but consolidation. A pass that would exceed either part of the review unit's bound is split into separate review units, not merely into more commits inside the same one, and not across concurrent sub-agents. Where the host pull request's own functional diff is large, the realignment moves out and becomes a standalone pass rather than sharing the reviewer's sitting; where it rides along, the admissible consolidation volume is the residual after the functional diff.
2. **Scope before classifying, and declare the scope.** Run the shared target-set selection script. Blanket scope is the failure mode, not the safe default. Record the resulting declared scope in the header of the classification record, together with the pass kind, the review-unit identity, the unit rule named from the closed enumeration, and the graph build state the target set came from; commit the target-set output inside the review unit, or ensure the gate can re-run it. Where a single file alone would exceed the bound, the declared scope is an explicitly enumerated subset of that file, the split reason is recorded so the target-set cross-check can pass, and the pass does not write `last-verified-at`.
3. **Record the verification baseline.** Capture the sha the pass is being verified against — `HEAD` after step 1's isolation and before any file is read — into the record header. This ordering is not incidental: capturing it before the functional work is committed would record a state the agent never examined, which is also why the functional work must be committed rather than stashed; capturing it after classification would record a state that includes the pass's own writes. It is what the coverage count is taken against, what `last-verified-at` will carry on a whole-document pass, what the gate's ancestry check floors, and what makes the pass reproducible either way.
4. **Classify. Do not rewrite yet.** Pass 1 labels every classifiable unit **in the declared scope** — per the declared unit rule — as exactly one of the following, applying the precedence order where more than one fits:
   - `contradicts code → suspected defect`
   - `not verifiable`
   - `historical decision → ADR`
   - `obsolete`
   - `still true`

   Write each label, with its churn-stable unit reference and its required citation or regenerability basis, into the structured classification record described above as the pass proceeds.
5. **Verify coverage, scope, baseline, and the judgement half of the bound — all before rewriting anything.** Run the checks against the classification record: classifiable units in the declared scope at the baseline sha in, classification entries out, counts must match; the declared scope cross-checked against the target set in both directions; the graph's build state checked for staleness; the baseline checked as parent of the first consolidation-class commit; and the removal-authorizing entry count checked against the judgement cap, which is knowable now because it does not depend on the rewrite. **This runs before the rewrite, not after** — a failure discovered after the rewrite costs the rewrite, and worse, invites the rewrite to be kept and the count to be reconciled to it. Be precise about what this buys: the count check defeats **omission within the declared scope** — the skipped section, the truncated pass — and nothing else. The cross-check raises the floor under scope plausibility but does not establish that the declared scope was *right*, which is why the scope is also stated where a reviewer sees it. Neither defeats **skimming**, because the agent that skims the middle of a long document can still emit one plausible label per unit and pass the count perfectly. Skimming is addressed by the citation requirement in step 4 plus a **human spot-check of a sample of entries against the file**, performed as part of the human review of the review unit and gating its merge: it is cheap, is not producible without having read the unit, and generalizes — entries whose citations do not hold indict the pass, not just the sample. Run all of it. A count-only check reported as coverage evidence is worse than no evidence, because it gets trusted.
6. **Rewrite.** Only now. Without the forcing pass in step 4 and the gates in step 5, the agent jumps straight to synthesis, and that is where loss occurs.
7. **Check the line half of the bound, and treat failure as re-scoping rather than as a finding to reconcile.** The removed-line count exists only after the rewrite, so this is the one check that necessarily follows the step it authorizes. Say so, and enumerate the admissible remedies in advance: split the pass across review units and re-run, or discard and re-scope. Raising the cap, redistributing across more commits inside the same review unit, and fanning out across agents are not remedies.
8. **Materialize the record inside the review unit, and keep it out of the persisted document and out of the consolidation commit.** The record never enters the document being consolidated. It is materialized through one of the two channels named above — rendered into the commit message body in a fixed machine-readable format, or committed as a retrieval-excluded file in its own commit, with the commit message carrying the counts and a pointer. Either way it is attached to the exact diff it describes, outside retrieval, and still available in six months when someone asks what the pass actually looked at. The sole content that crosses from the classification into the document is the `not verifiable` bucket, as the `## To be confirmed` section described in step 11 — items, not the record, and only that bucket. The size threshold at which the committed-file channel becomes preferable to the commit message body is left open. Rationale for exhaustiveness: if the agent flags only what it believes obsolete, silence becomes ambiguous between "verified, current" and "never examined" — two radically different things the human cannot distinguish. And "never examined" is the common case, because attention over a long document is not uniform: agents work well at the beginning and the end and skim the middle. Exhaustive classification is a forcing function that makes **coverage** visible. The verdict per unit matters less than the guarantee that every unit in scope was looked at.
9. **Verify against the code, not against the document.** Nothing survives unless it is verifiable in the current code or is a genuine decision, constraint, or rationale. The code is the truth about *what it does*; the unique value of documents is the *why* and what was rejected.
10. **`contradicts code → suspected defect` is never resolved by the agent.** The comment or statement is left in place, unmodified, at the granularity of the whole declared unit, and the divergence is reported — into the escalation intake, not only into the transcript, and not a second time if a suppressing entry already exists for it.  Rewriting documentation to match code that may itself be wrong is the one failure mode that produces a clean diff and a worse system.
11. **`not verifiable` is the critical bucket.** It is never deleted silently. In a document pass it goes into a `## To be confirmed` section in the document *and* into the escalation intake. That section legitimately belongs in the persisted document because it is open work assigned to a person, which is not current state — that is the ground of the exception, not a metadata carve-out. In a comment pass there is no in-file carrier and none is created: the comment is left byte-for-byte unmodified and the escalation travels through the intake and the classification record alone. In either case the freeze applies to the whole declared unit, and in either case the escalation is subject to read-before-append against a churn-stable reference.
12. **Review the removed lines, not the result.** Reading the final document does not reveal what was lost; reading the `-` lines does. Read them against the classification record: a `-` line with no corresponding entry is a hole the coverage count cannot catch. This step and the entry spot-check in step 5 together constitute the review budget of the unit, and they are the only real control on the regenerability test — which is why the bound in step 1 exists: a diff too large to read, or carrying more independent removal judgements than a reviewer will actually adjudicate, is a review that did not happen.

### Triggers

Correct:

- completion of a feature or epic (the plan dies; what it taught flows back into the spec);
- **at the start of brainstorming on an area touched in the past** — this grafts onto the existing workflow and yields clean context before the most token-expensive phase, and is the case where the consolidation commit stands alone rather than riding inside a feature PR;
- whenever the agent is observed citing obsolete information — the most reliable diagnostic signal.

Wrong: **mid-implementation. Never.**

**The obsolete-citation trigger is a signal, not an authorization, and the deliverables must say so.** It arrives mid-implementation more often than not, which is precisely where consolidation is prohibited. The resolution: the observation is **recorded into the escalation intake when it happens, and consumed at the next admissible boundary** — feature completion, or the next entry into brainstorming on that area. Observing the signal never licenses an immediate mid-implementation pass, and an intake entry is what stops the signal from being lost while it waits.

Calendar-based triggers are inferior to event-based ones. Doing it "by feel every once in a while" is the worst mode, because information loss happens precisely when no checklist is in play.

### The asymmetry that must be explicit

The naïve two-tier version — "technical details the agent decides, business rules it escalates" — is insufficient, because it hands the agent authority over cases where it can see a fact but not interpret it. Encode **three tiers**:

| Tier | Truth source | Agent authority |
|---|---|---|
| **Code-verifiable** | The code, unambiguously | Decides autonomously. Redundant comments deleted, obsolete statements rewritten, stacked layers collapsed. |
| **Code-visible, intent-ambiguous** | The code shows a divergence, but not which side is correct | **Reports, does not resolve.** A comment/spec statement that contradicts the code is a suspected defect, not a stale document. |
| **External truth** | Business rules, regulation, contracts — outside the repository | **Escalates.** No autonomous deletion under any circumstance. |

The middle tier is the one that gets omitted and the one that causes the most expensive failures. Without the top tier's boundary made explicit, the outcome is technically impeccable consolidations that delete a regulatory constraint nobody had implemented yet — a deletion invisible in review precisely because it is technically correct. Without the middle tier, the outcome is documentation quietly rewritten to describe a bug as intended behavior.

Both lower tiers terminate in the same place: the escalation intake. A tier distinction that does not end in a durable destination is a taxonomy, not a control.

The outer tier is not the rare case. Both skills meet it routinely, and they differ only in what it does to the pass — a stop condition for comments, arbitrable work for specs, per the skill definitions above.

**Present the table with its limitation attached**, per the settled position above: the tiers partition authority, they do not independently verify the judgement that assigns a unit to a tier.

### Critical positions to carry into the project — do not soften these

- **The optimization target is upstream, not downstream.** Reducing after the fact costs far more than not accumulating in the first place. If only one thing gets built, it is append-resistant documents by construction. The consolidation skills are maintenance, not the solution.
- **Many documents should not be compacted — they should be removed from play.** A significant share of documentation in an AI-assisted codebase is write-once, read-never: produced because producing it was cheap. The question to ask of every file is "if this disappeared, what would break?" Aggressive removal returns more than accurate compaction, and costs less. Execute it as retrieval exclusion first and deletion second: the context-cost benefit is captured by exclusion **provided every channel is closed — inbound references and the agent's routine search scope included**. An excluded file still linked from a live document, or still returned by the agent's default grep, is still in play, and in that state the benefit has not been captured and the case for deletion is not answered.
- **The return on comment consolidation is bounded in a way the return on document exclusion is not, and this should temper how it is prioritized.** Excluding a document removes it from retrieval entirely — the tokens are simply never spent. Comments, by contrast, are only ever read as part of a file the agent was going to read anyway, so consolidating them shortens files already in scope rather than removing anything from scope. The saving is real but second-order, while the characteristic failure — a deleted invariant — is first-order. Two further compressions of that return are settled above and must be carried here: the conservative reconstructor standard makes most comments non-regenerable, and whole-unit freezing forfeits redundancy inside frozen units. This does not overturn the prediction below that comment debt is the largest and the comment skill the likeliest to be demanded; it does mean the demand *and* the yield should be confirmed by measurement rather than assumed, and that document exclusion is the cheaper first move even where comment debt looks worse.
- **The enemy is not length, it is contradiction.** A long, coherent, true document costs tokens. A short one with three conflicting statements costs correctness — and hours spent working out why the agent implemented the wrong rule. Optimize non-contradiction first, brevity second.
- **Both skills are, first and foremost, scoping problems.** The expensive part is not rewriting; it is deciding which files to work on. Blanket-consolidating a large module is the most reliable way to blow the context window and get a shallow pass through the middle. The target-set selection strategy must be defined before the procedure, must live in shared machinery rather than in each skill's prose, and the existing knowledge graph is the natural instrument for it — subject to the graph's own staleness invalidating the control rather than merely weakening it, and subject to the target set reaching the gate by a path that is not the agent's narration. This determines whether the skills are usable or merely elegant.
- **Every control in this design must be mechanical or it is not a control.** Coverage checks, the two-part bound, plan status marking, retrieval exclusion: each is a place where the agent's self-report is not evidence. Where a script can verify a claim, the script is mandatory and the claim is not accepted on its own. A control whose input does not exist — a coverage check with nothing to count, an escalation with nowhere to land, a gate check reading a record that was never materialized — is the same failure in a more flattering shape. So is a control whose parameters are supplied by the party being controlled, unless something not agent-authored puts a floor under them; so is a control whose non-agent-authored floor is stale; and so is a control that compares two numbers the controlled party produced.
- **Mechanical is necessary and not sufficient: a check must also measure the property it is credited with.** A well-formed script counting the right number of the wrong thing is more dangerous than no script, because it converts a suspicion into a passing build. Every control in the deliverables therefore states what it verifies **and what it does not** — the count check catches omission within the declared scope and not skimming; the target-set cross-check raises the floor under scope plausibility without establishing that the scope was right, and only where the graph is fresh and the target set did not arrive by narration; the baseline ancestry check floors which tree was counted and says nothing about whether it was read; the removed-line cap bounds reading volume and says nothing about whether the removals were correct; the removal-judgement cap bounds judgement volume and equally says nothing about correctness; `last-verified-at` measures distance from the verified state and not the quality of the verification, is absent rather than approximate after a subset pass, and is absent rather than dangling where the sha would not survive merge; the tier table partitions authority and does not validate tier assignment. Where a control's stated property and its actual property diverge, the divergence is a defect in the design and not a caveat.
- **Check ordering is part of a control's specification, and the one unavoidable exception is stated rather than hidden.** A verification that runs after the irreversible step it was meant to authorize is a report, not a gate. Every check in this design is placed before the step it authorizes, with exactly one exception — the removed-line half of the bound, which cannot exist before the rewrite — and that exception ships with enumerated remedies precisely so that the pressure to reconcile the work to the check has a pre-agreed answer.
- **Human review capacity is a single budget with several claims on it.** The removed-line cap, the removal-judgement cap, the `-` line reading, the entry spot-check, and — in the merge-time case — the functional diff sharing the sitting are not five independent safeguards; they are five demands on the attention of one reviewer in one pass. Any proposal that tightens one by loosening another has not improved the design, and any numeric calibration that sets one without the others is incomplete by construction. The unit rule's granularity is a claim on the same budget, and so is the number of review units produced per week — which is why concurrency across review units is barred.
- **The observation window must be instrumented before it opens, or it is not diagnostic — and the instrumentation is partly conditional.** The sequencing below claims the first shipment is diagnostic and that roughly two weeks of observation reveal which skill is actually needed. That claim is only true if something is being measured; without a baseline captured before the rules land, the window produces impressions and a recollection of impressions. The **minimal baseline capture ships with the rules**, in two parts that must not be conflated:
  - **Unconditional:** intake entry counts by kind and by state. This requires nothing but the intake and is implementable the day the rules ship.
  - **Conditional on toolchain observability:** the composition of retrieved context per session by artifact type. This depends on the retrieval channels being introspectable, which is itself open below. Where they are not, the deliverables must specify a **defined manual sampling procedure** as the fallback and state that the comment-versus-exclusion priority is calibrated from a sample rather than from a census — not silently drop the measurement and keep the claim.
  - **Neither part calibrates the review budget, and the deliverables must not pretend otherwise.** Intake counts and retrieval composition say nothing about how many removed lines a reviewer reads before quality falls off. The review-budget numbers require their own exercise: a small number of deliberately measured review passes over consolidation-shaped diffs, recording volume, time, and defects caught. Name that exercise as a separate prerequisite of shipping either skill; do not attribute those numbers to the observation window, which does not produce them.
- **Recommended sequencing:** ship the rules first, together with the escalation intake they depend on, **the retrieval-exclusion and plan-archiving machinery**, and **the baseline measurement capture**, and build neither skill for roughly two weeks. All four are cheap, non-destructive in their first phase, and independently valuable; the exclusion machinery in particular is the highest return-per-unit-risk item in the design, and withholding it during the observation window would be withholding the intervention most likely to make the skills unnecessary. Two scoping caveats are load-bearing and must be stated rather than glossed. First, phase-one exclusion requires severing inbound references, and whether that is safely agent-executable is open below, so in the first shipment **the severance is performed by a human** while the exclusion configuration itself is scripted — which means the exclusion benefit accrues at human throughput until that question closes, qualifying the return-per-unit-risk claim without overturning it, and making the closing of that question the highest-value item on the open list. A human-performed severance is still a reviewed destructive edit carrying its own classification record, and **the reviewer is not its author**: self-review of one's own deletions is precisely the self-report failure this design refuses everywhere else, and where no second reviewer is available the severance is deferred rather than self-reviewed. Second, the exclusion benefit is conditional on the agent's routine search scope being constrainable; where it is not, the first shipment's headline claim is weaker than stated and the deliverables say so. Rules are the highest value-to-cost intervention and they are *diagnostic* — after two weeks of observation it becomes clear which of the two skills is actually needed and which was imagined for symmetry. Expected outcome (a prediction, worth less than the observation): rules absorb most of the problem on new documents, exclusion absorbs much of the remaining context cost, and the skill actually needed is the comment one, where pre-existing debt is largest and rules do not reach retroactively. **Read this as a prediction about demand, not about safety and not about yield** — the comment skill is the likeliest to be demanded first, simultaneously the one whose failure mode is most expensive, and the one whose per-pass yield the conservative standards deliberately compress, which is why the two-part bound, the per-deletion regenerability basis, and the conservative reading of the regenerability test ship *with* it rather than after it. The observation window is also the window in which the intake produces the first evidence about how often the middle and outer tiers actually fire, and about how often the obsolete-citation signal fires at all; if it produces none, that is a finding about the rules, not a reason to skip the intake.
- **Specified is not scheduled.** Both skills are fully specified in the project knowledge document; only the rules, the intake, the mechanical machinery, and the measurement capture are scheduled first. Specifying both is cheap, sharpens the rules by forcing the boundaries to be drawn, and costs nothing as long as neither is built during the observation window. Do not read the sequencing advice as a reason to leave a skill under-specified.
